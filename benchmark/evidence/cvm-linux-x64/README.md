# 独占云服务器上的复测证据（2026-10-12，CVM）

本目录是 2026-10-12 在一台新开的独占云服务器（CVM）上的实测数据。它和 `benchmark/evidence/devcloud-linux-x64/`（共享宿主上的 32 核配额容器）不是同一环境，物理核数、CPU 代际和存储都不同，**绝对数字不能横向比较**；两边可以对照的只有“同一机器内 A/B 的方向和幅度”。

## 云盘 IOPS 限住了落库（12:03 停掉的第一轮）

第一轮按原样（中间件数据在云盘 `vdb` 上）跑 e2a6f96 对 b374ef2 的 A/B，在第 1 组 baseline 的三档之后手动停掉。三档窗口内磁盘每秒写 IO 的中位数为 3281–3574，利用率 95.4–96.6%，写等待约 0.5 ms，1000/s 那一档就已经打满。按腾讯云高性能云盘的性能公式，50 GB 的随机 IOPS 上限是 1800 + 30 × 50 = 3300。

| 到达率 | 丢弃 | 系统错误率 | HTTP p99 ms | 窗口内落库（平均每秒） |
|---|---|---|---|---|
| 1000 | 0 | 0 | 16 | 821 |
| 2000 | 0 | 0 | 182 | 1058 |
| 2500 | 12.5% | 6.0% | 2452 | 1164 |

MySQL 每次提交都要刷 redo 和 binlog，RabbitMQ 的持久化消息、Redis 的 RDB 也写这块盘。用窗口内写 IOPS 除以落库速度粗算，每落一单约 2.9–4.4 次写 IO（并发越高，组提交摊得越多），所以落库被限在每秒约 1000 单，远低于应用和 CPU 的能力。这个环境下比较 Redis 侧的优化会被磁盘掩盖，因此把三个中间件的数据目录换成 tmpfs 后重来：MySQL 的刷盘参数不变，只是 fsync 落在内存里。之后各轮比较的是代码路径和 CPU，不代表真实云盘部署的落库能力。

这一轮的原始包保留在新机器 `/data/ms/results/pool-budget-20261012-115446-b374ef27-50010.tar.gz`，本目录只摘录上表。

# 窗口中段“约 1 秒连接池全满”的排查：根因是 InnoDB 默认的 redo 与 buffer pool 太小

原容器的预热验证里记录过：1000/s 窗口中段偶尔有约一秒 40 条连接全满、请求排队，时间点不固定。本机两组 A/B 同样出现，上面第一组 1000/s、2000/s 的 12 个窗口中有 7 次：

- 形态都一样：前后几秒池里通常只用 4–13 条连接（有一次前一秒是 29 条），某一个 1 秒采样点池里当时的全部连接（37–40 条）同时被占用、排队 7–139 个，下一个采样点就恢复。139 个排队按 2000 req/s 折算约 70 ms 没有连接归还，像一次亚秒级的数据库侧停顿。这是独占虚拟机，不是共享宿主的噪声。
- 不是 GC：两组 JVM 都开了 GC 日志（`-Xlog:gc`），1000/s 时每 3–4 秒一次 10–14 ms 的年轻代停顿；有一次全满（排队 39）前 1.5 秒内没有任何 GC 停顿，其余几次附近的停顿也只有 10–14 ms，撑不出几十到一百多个排队。
- 不是每分钟一次的库存对账：全满时刻与最近一次 `COORD_REPAIR` 日志相差 2–30 秒。
- 不是 binlog 切换：本机为 tmpfs 设了 256 MB 切分，2000/s 时约 40 秒切一次，频率和全满次数接近，于是做了 `binlog-probe-20261012-134945`（脚本 `binlog-probe.sh`）：优化版 jar，2000/s 恒定 150 秒，窗口开始后第 20、50、80、110 秒各执行一次 `FLUSH BINARY LOGS`，10 Hz 采 Hikari 排队数和 binlog 文件切换时刻。4 次切换前后 2 秒内排队都是 0；整个窗口只有 1 秒排队数为 1，当时只有 11 条连接在用（池子在补连接），与“40 条同时被占用”不是一回事。这 150 秒里也没有出现一次全满。

影响在几毫秒以内：2000/s 有全满的 4 个窗口 HTTP p99 为 22.8–27.7 ms，没有的 2 个窗口为 20.9–21.7 ms；1000/s 看不出差别。

**10 Hz 多路探针（stall-probe-20261012-145737，脚本 `stall-probe.sh`）。** main 的 jar，2000/s 恒定 480 秒，同时以 10 Hz 采：Hikari 在用/排队；MySQL 的 Threads_running、行锁等待、脏页、`Innodb_buffer_pool_wait_free`、检查点年龄与异步/同步刷脏阈值（`information_schema.INNODB_METRICS`）；`/proc/pressure` 的 CPU/内存/IO 压力和 CPU steal；JVM 另开 `-Xlog:gc*,safepoint`；Tomcat 访问日志记毫秒级起止时间。窗口内“所有连接占满且有排队”的片段 3 次：

| 时刻 | 排队峰值 | 同时刻的 MySQL | 其他信号 |
|---|---|---|---|
| +63.5 s | 7 | 检查点年龄 78.9 MB（异步阈值 77.5 MB、同步阈值 83.1 MB） | 附近 GC 10.6 ms |
| +78.5 s | 73 | 检查点年龄 81.0 MB | 附近 GC 10.8 ms；跨过片段起点的请求最长 78 ms |
| +441 s | 5 | 42 个线程都在 MySQL 里执行，前后 2 秒内 `wait_free` 增加 1372 | GC 32 ms；跨过起点的请求最长 160 ms |

- redo 容量是默认 100 MB。整个窗口里检查点年龄每 20 秒都冲到约 83 MB，即同步刷脏阈值，27% 的时间超过异步阈值的 90%；buffer pool 是默认 128 MB，跑到 280 秒后表变大，空闲页等待开始累积，440 秒那 20 秒共 1537 次。
- PSI 和 steal 全程为 0；JVM 等安全点最长 36 ms；访问日志里片段前后任何 50 ms 内开始的请求最多 260 个（平均约 200），不是压测端突然打来一批。跨过片段起点、持续 78–160 ms 的请求说明是服务端在处理中途卡住。

**对照（stall-probe-20261012-150853）。** 在线把 `innodb_redo_log_capacity` 调到 2 GB、`innodb_buffer_pool_size` 调到 4 GB，其余不变，用同一个 jar 再跑同样的探针，跑完恢复默认值。

| | 默认（100 MB / 128 MB） | 调大（2 GB / 4 GB） |
|---|---|---|
| 检查点年龄峰值 | 83 MB（顶到同步阈值） | 545 MB（异步阈值 1591 MB 的 34%） |
| 空闲页等待 | 窗口内上千次 | 0 |
| Threads_running ≥ 40 的采样 | 26 / 4712 | 1 / 4712 |
| Hikari 有排队的采样 / 排队峰值 | 75 / 73 | 43 / 16 |
| HTTP p95 / p99 | 7.6 / 40 ms | 5.0 / 45 ms |

调大后剩下的 2 次占满（排队 2、16）都和 MySQL 无关：一次是 JVM 进入 Cleanup 安全点前等了 80 ms，一次在 30 ms 的 G1 停顿之后；这次的 p99 由这些 JVM 停顿决定，而且只是单次运行。

结论：压测里的偶发全满主要来自 MySQL 默认的 redo 容量和 buffer pool 太小。写入压力下检查点年龄反复冲到同步刷脏阈值，表变大后再叠加空闲页等待，所有写连接一起卡住几十毫秒，40 条连接同时被占用、请求排队；调大这两项后这类片段消失。所有 A/B 的标准配置仍保持 MySQL 默认值，以便和之前的证据对比；生产或长时间压测应按写入量设置 redo 容量与 buffer pool。原容器同样是 MySQL 8.0 默认配置，推断是同一原因，那边没有做对照。

# 本目录的结论

- 新机器的 50 GB 云盘约 3300 IOPS，原样部署时落库每秒约 1000 单就到顶；中间件数据放 tmpfs 后才进入 CPU 受限区间。容量规划时，落库能力要按“每单写 IO 次数 × 磁盘 IOPS 上限”单独估算。
- 接纳合并（`cb567fb`）在本机把入口稳定档从 3000 提到 3500/s（对 main，三轮一致），与同机改造前持平；九场景正确性复测 9/9。
- Redis 在另一台机器上时，少两次往返的收益更直接：0.6 ms 往返下，1000/s 下单中位少 1.5 ms，3000/s 少 8–9 ms。
- 协议在 Redis 侧仍有代价（同档 CPU 约为改造前 1.6–1.9 倍），主要来自预扣时校验 128 个分桶；单主部署关闭分桶可省 25%–38% 的 Redis CPU，不分桶模式九场景 9/9，但入口稳定档没有因此提高。
- 本机 3500/s 的拐点在 RabbitMQ 发布端：Boot 默认只缓存 25 个 channel，多出来的并发发送每次都开关一个 confirm channel。缓存调到 256 后（已写入默认配置）稳定档 3500 → 4000/s，3500/s 的首次发送从约 20 ms 降到 2.4–3.1 ms、负载期落库多约两成。
- 压测里偶发的“连接池约 1 秒全满”来自 MySQL 默认 100 MB redo 与 128 MB buffer pool：检查点年龄顶到同步刷脏阈值、表变大后再加空闲页等待；调到 2 GB / 4 GB 后消失。标准压测仍用默认值以便对比。
- 同一台机器上把 40 条连接拆给三个 JVM 更差（稳定档 2000–3000/s 对 3500/s）：池子拆小、消费者并发翻三倍、JVM 开销多 30%–47%。多实例要带来容量，前提是多台机器且下游有余量。
