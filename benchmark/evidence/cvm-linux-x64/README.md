## 云盘 IOPS 限住了落库（12:03 停掉的第一轮）

第一轮按原样（中间件数据在云盘 `vdb` 上）跑 e2a6f96 对 b374ef2 的 A/B，在第 1 组 baseline 的三档之后手动停掉。三档窗口内磁盘每秒写 IO 的中位数为 3281–3574，利用率 95.4–96.6%，写等待约 0.5 ms，1000/s 那一档就已经打满。按腾讯云高性能云盘的性能公式，50 GB 的随机 IOPS 上限是 1800 + 30 × 50 = 3300。

| 到达率 | 丢弃 | 系统错误率 | HTTP p99 ms | 窗口内落库（平均每秒） |
|---|---|---|---|---|
| 1000 | 0 | 0 | 16 | 821 |
| 2000 | 0 | 0 | 182 | 1058 |
| 2500 | 12.5% | 6.0% | 2452 | 1164 |

MySQL 每次提交都要刷 redo 和 binlog，RabbitMQ 的持久化消息、Redis 的 RDB 也写这块盘。用窗口内写 IOPS 除以落库速度粗算，每落一单约 2.9–4.4 次写 IO（并发越高，组提交摊得越多），所以落库被限在每秒约 1000 单，远低于应用和 CPU 的能力。这个环境下比较 Redis 侧的优化会被磁盘掩盖，因此把三个中间件的数据目录换成 tmpfs 后重来：MySQL 的刷盘参数不变，只是 fsync 落在内存里。之后各轮比较的是代码路径和 CPU，不代表真实云盘部署的落库能力。

这一轮的原始包保留在新机器 `/data/ms/results/pool-budget-20261012-115446-b374ef27-50010.tar.gz`，本目录只摘录上表。

# 窗口中段“约 1 秒连接池全满”的排查（未找到根因）

原容器的预热验证里记录过：1000/s 窗口中段偶尔有约一秒 40 条连接全满、请求排队，时间点不固定。本机两组 A/B 同样出现，上面第一组 1000/s、2000/s 的 12 个窗口中有 7 次：

- 形态都一样：前后几秒池里通常只用 4–13 条连接（有一次前一秒是 29 条），某一个 1 秒采样点池里当时的全部连接（37–40 条）同时被占用、排队 7–139 个，下一个采样点就恢复。139 个排队按 2000 req/s 折算约 70 ms 没有连接归还，像一次亚秒级的数据库侧停顿。这是独占虚拟机，不是共享宿主的噪声。
- 不是 GC：两组 JVM 都开了 GC 日志（`-Xlog:gc`），1000/s 时每 3–4 秒一次 10–14 ms 的年轻代停顿；有一次全满（排队 39）前 1.5 秒内没有任何 GC 停顿，其余几次附近的停顿也只有 10–14 ms，撑不出几十到一百多个排队。
- 不是每分钟一次的库存对账：全满时刻与最近一次 `COORD_REPAIR` 日志相差 2–30 秒。
- 不是 binlog 切换：本机为 tmpfs 设了 256 MB 切分，2000/s 时约 40 秒切一次，频率和全满次数接近，于是做了 `binlog-probe-20261012-134945`（脚本 `binlog-probe.sh`）：优化版 jar，2000/s 恒定 150 秒，窗口开始后第 20、50、80、110 秒各执行一次 `FLUSH BINARY LOGS`，10 Hz 采 Hikari 排队数和 binlog 文件切换时刻。4 次切换前后 2 秒内排队都是 0；整个窗口只有 1 秒排队数为 1，当时只有 11 条连接在用（池子在补连接），与“40 条同时被占用”不是一回事。这 150 秒里也没有出现一次全满。

结论只到这里：全满是偶发、亚秒级、所有连接同时卡住，已排除 GC、对账任务和 binlog 切换。影响在几毫秒以内：2000/s 有全满的 4 个窗口 HTTP p99 为 22.8–27.7 ms，没有的 2 个窗口为 20.9–21.7 ms；1000/s 看不出差别。要继续查，需要在出现时同时抓 MySQL 内部等待（如 performance_schema 的锁和刷盘等待）或内核侧调度与内存分配延迟。

# Redis 不在本机时：只给 Redis 加网络延迟的 A/B（accept-ab-redis-rtt-a1e8d926，2026-10-12 13:55–14:37）

# 本目录的结论

- 新机器的 50 GB 云盘约 3300 IOPS，原样部署时落库每秒约 1000 单就到顶；中间件数据放 tmpfs 后才进入 CPU 受限区间。容量规划时，落库能力要按“每单写 IO 次数 × 磁盘 IOPS 上限”单独估算。
- 接纳合并（`cb567fb`）在本机把入口稳定档从 3000 提到 3500/s（对 main，三轮一致），与同机改造前持平；九场景正确性复测 9/9。
- Redis 在另一台机器上时，少两次往返的收益更直接：0.6 ms 往返下，1000/s 下单中位少 1.5 ms，3000/s 少 8–9 ms。
- 仍有的代价在 Redis 侧（同档 CPU 约为改造前 1.6–1.9 倍），主要来自预扣时校验 128 个分桶。
