# 单实例容量摸底原始证据（2026-10-09，Linux 容器）

本目录是 2026-10-09 在一台 Linux 开发容器上的实测原始数据。它与 `benchmark/evidence/mac-arm64/` 的 2026-07 Mac M1 结果不是同一环境，**不能横向比较**；`REPORT.md`、`REPORT-RELIABILITY.md` 的历史数字不因本目录改变。

## 环境

| 项 | 实际值 |
|---|---|
| 机器 | 非特权 Linux 容器，TencentOS Server 3.2；宿主 AMD EPYC 9K65 192 核（共享）；cgroup CPU 配额 32 核（`cfs_quota=3200000/100000`），内存上限 64 GB；数据盘 `/data` |
| 中间件 | **原生进程，不是容器**（容器内无法运行 Docker）：MySQL 8.0.46（`--max-connections=300`，其余默认，含 binlog 与每次提交刷盘）、Redis 7.2.7（源码编译，默认配置）、RabbitMQ 3.13.7 + Erlang 26.2.5.19 |
| 应用 | 单实例 `java -Xms2g -Xmx2g -jar`，参数同 `REPORT.md` 第 9 节：`--spring.profiles.active=100k`，关闭业务限流、anti-brush、动态限流，`MINI_SECKILL_WORKER_ID=7`；JDK 17.0.20.1 |
| 压测 | k6 v2.3.0，与应用、中间件在同一容器内，共用 32 核配额 |
| 版本 | 新版 `deb719a`（= PR #1 合并后 main，代码同 `09906d2`）与旧版 `68858ab`；jar SHA-256 见 `jars.sha256` |

搭建与运行脚本在 `benchmark/native-linux/`：`services.sh` 启停三个中间件，`docker` 是把既有脚本里的 `docker exec/stop/start mini-seckill-*` 转发到本机进程的转发脚本，`cap-step.sh` 做阶梯加压，`ab-rounds.sh` 做交错对照，`diag-knee.sh` 在拐点抓线程栈和 MySQL 状态。

## 方法

- 场景只用 `unique`（每次迭代一个新用户，先领 token 再下单），每档到达率恒定 60 秒。每档前用 `benchmark/reset-env.sh` 重置，库存设为该档总迭代数的 2 倍，保证所有请求都走完整的成功入队路径（最重路径），不会提前售罄。
- 每秒采样一次 MySQL 订单数和各进程 CPU（`/proc` 差分，100% = 1 核）。k6 结束后等待订单数追上入队数，记录追平时间。每档结束跑 `run-verify.sh` 对账。
- 停止条件：系统错误率 > 1% 或丢弃迭代 > 1%。
- 一次迭代 = 2 个 HTTP 请求（token + order），所以 HTTP 请求速率约为到达率的 2 倍。

## 拐点处的线程栈（新版，3000/s）

`diag-new-r3000/`：在 3000/s 持续 40 秒的第 15、25 秒各抓一次 `jstack`（原文压缩为 `.gz`）和 MySQL 状态。Tomcat 共 200 个工作线程（默认上限），全部在忙：

| 等待位置（Hikari 借连接 ← 应用调用点） | 第 15 秒 | 第 25 秒 |
|---|---|---|
| `ConcurrentBag.borrow` ← `ActivityServiceImpl.assertRunning` | 74 | 87 |
| `ConcurrentBag.borrow` ← `SeckillServiceImpl.hasAcceptedOrFinishedOrder` | 57 | 34 |
| `ConcurrentBag.borrow` ← `SeckillServiceImpl.placeOrder` | 32 | 24 |
| `ConcurrentBag.borrow` ← `SeckillProducer.send` | 24 | 27 |
| 正在执行 SQL（`placeOrder` / `SeckillProducer.send`） | 8 | 23 |

同时 MySQL `Threads_running` 为 41、42，与 100k profile 的 `hikari.maximum-pool-size: 40` 一致；`Innodb_log_waits` 为 0。进程 CPU 合计约 18 核，未达到 32 核配额。

## 按代码数出的每单数据库往返（非实测，供分析）

一次成功迭代在入口线程上的同步数据库操作：token 接口 `assertRunning` 查活动 1 次、`hasAcceptedOrFinishedOrder` 对新用户回源查订单 1 次；order 接口 `assertRunning` 再查活动 1 次、`placeOrder` 插本地消息 1 次、`SeckillProducer.send` 的 `markSending` 1 次。另有 publisher confirm 回调的 `markSentFromSending`，以及消费者的抢占 CAS 与落库事务。入口和消费者共用同一个 40 连接的 Hikari 池（消费者并发 8–32）。

## 可以由这些数据支持的结论

- 在这台机器、这套配置下，单实例入口在 2000/s 时无错误、无丢弃；3000/s 处于临界，三次中两次出现丢弃（其中一次伴随 10% 超时），一次全部通过。
- 拐点处 Tomcat 线程几乎全部在等 Hikari 连接，CPU 未打满。
- 消费落库在 2000/s 以上跟不上入口，k6 结束时已落库 54%–100%，之后 7–33 秒追平；所有轮次最终订单与入队一致。
- 三组新旧对照互有胜负，单版本前后波动大于版本差，**未测出 PR #1 带来的性能差异**；宿主共享，噪声较大。

未做：4000/s 以上（停止条件已触发）、多实例、提交后 ACK 丢失与 Redis 投影失败的精确切点演练。

## 环境噪声：共享数据盘的写入卡顿

本轮宿主磁盘明显比下午嘈杂。失败档里反复出现同一特征：java 与 mysqld 的 CPU 同时跌到 100% 以下、每秒落库跌近 0，同一秒数据盘写入平均等待从约 0.3 ms 升到 7–37 ms（每次提交刷盘的 MySQL 整体停顿），接着连接池被占满、2 秒借连接超时。

下面按“负载窗口内写入等待 > 2 ms 的秒数”分组。**这个分组阈值（≥ 5 秒算卡顿档）是看过数据之后定的**，所以所有档都在三份表里原样保留，这里只是辅助阅读：

- 卡顿 ≥ 5 秒的 7 档全部失败：新版第二组第 1、2 轮 1000/s（28、15 秒）、deb719a 第二组第 1、2 轮 2000/s（9、34 秒）、消融 both-on 第 1 轮 4000/s（7 秒）、cache-only 第 2 轮 1000/s（25 秒）、fuse-only 第 1 轮 1000/s（26 秒）。
- 没有磁盘数据的 3 个失败档无法归因：第一组新版第 1、2 轮 2000/s（逐秒数据有同样的 CPU 同时塌陷特征，但没有磁盘数据佐证），deb719a 第 1 轮 1000/s。

## 结果一：入口 60 秒稳定档 3000 → 4000/s

只看有磁盘数据且卡顿 < 5 秒的档，按到达率统计通过数：

| 配置 | 1000 | 2000 | 3000 | 4000 | 5000 |
|---|---|---|---|---|---|
| deb719a（两组 A/B） | 4/4 | 2/2 | 2/2 | **0/3**（系统错误率 33%、56%、33%） | 未到 |
| 新 jar 两项关闭 both-off（消融） | 2/2 | 2/2 | 2/2 | **0/2**（35%、34%） | 未到 |
| 新 jar 默认 both-on（A/B 新版 + 消融 both-on） | 4/4 | 4/4 | 4/4 | **3/3** | **0/3**（丢弃 5.6%、7.1%、7.4%） |

另外 deb719a 第一组第 2 轮（无磁盘数据）3000/s 通过、4000/s 失败（该档有磁盘数据、0 秒卡顿，已计入上表）。

所以在这台机器、这套口径下：deb719a 与 both-off 在 3000/s 能通过、4000/s 大面积超时；默认配置 4000/s 三次全过（HTTP p99 98.6–108.0 ms），5000/s 三次都超过 1% 丢弃。**入口 60 秒突发稳定档从 3000/s 提到 4000/s，临界在 4000–5000/s 之间。** 上文历史表里 deb719a 3000/s 三次两次丢弃，本轮低卡顿窗口里三次通过，同一版本前后差异依旧很大。

1000/s 低负载时的整池借连接次数/迭代，正好按代码计数一级级下降：deb719a 8.95–9.62、both-off 9.52/9.59、fuse-only 8.51（少 1 次）、cache-only 7.50（少 2 次）、默认 6.54–6.69（少 3 次）。默认配置每档实际活动查库约 233 次/60 秒（约 3.9 次/秒），与 PR 估算的 `1/0.25s` 一致；`seckill_activity_cache_total` 的 miss 数含合并等待，比查库次数多。

结论：

- 收益主要来自首次 INSERT SENDING 融合。只融合（省 1 次写提交）就把 3000/s 的 p99 从 517–583 ms 降到 75 ms、负载期落库从约 1300/s 提到 2305/s；只开活动缓存（省 2 次主键读）p99 降到 220 ms，负载期落库基本不变。两项一起最好。
- 原因推断（未单独测量提交耗时）：被省掉的 `markSending` 是一次独立写提交，在每次提交刷盘的 MySQL 上要排队等刷盘，持有连接的成本远高于活动表主键读。所以“省几次 SQL”不能直接换算收益，写提交比读贵得多。
- 3000/s 两次线程栈快照（`jstack-classify.txt`）：200 个 Tomcat 线程中，deb719a 历史快照 187、172 个在等 Hikari；新版 0–2 个在等，185–187 个空闲在线程池里。4000/s 第 25 秒重新出现 65 个等待（消息 INSERT 36、token 回源查订单 29），下一个瓶颈是这两条保留的同步 SQL。快照是瞬时值，Hikari 等待以每秒采样的均值为准。

## 结果三：端到端持续完成能力只提高了一部分

- 2000/s 时两版本都不积压（低卡顿档队列 ready 峰值 0，负载期 SUCCESS ≈ 2000/s）。
- 3000/s 时两版本都积压，默认配置负载期落库 2310–2556/s，deb719a 1313–1392/s，停流后追平 5–9 秒对 20–23 秒。**两个版本都跟不上 3000/s 的持续到达**，持续完成上限都在 2000–3000/s 之间，本轮没有细分这一段。
- 新版入口放进来的越多，负载期落库越慢：默认配置 3000/s 约 2300–2550/s、4000/s 约 1630–1740/s、5000/s 约 1260–1310/s；4000/s 的队列峰值 13–14 万条，停流后 27–30 秒追平。停流后消费者单独追平速度约 4.3–4.8 千条/秒（两版本相近），说明负载期落库变慢是入口和消费者抢同一个 40 连接池，不是消费者本身慢。
- 因此本轮能说的是：**入口突发承载提高了（稳定档 3000 → 4000/s），3000/s 下负载期落库速率是 deb719a 的 1.7–1.9 倍；但入口收得越多、积压越大，端到端持续完成能力没有随入口同比提高。** 下一步应在固定 40 连接总预算内做入口/消费者的并发隔离或限额实验。

## 正确性对账与一个既有消费者缺陷

- 全部档（含失败档）业务键重复组 0、订单号重复 0。通过的档订单数等于 k6 入队数，消息全部 CONSUMED。
- 失败档里 k6 记录的入队数少于库里订单数（客户端 5 秒超时放弃了、服务端仍然受理），`cap-step.sh` 按客户端入队数判断追平，所以这些档的 verify 可能在消费追平前就跑了，表里“非终态”消息多是这一时刻的快照，不能当成最终状态。
- 真正卡住的只确认到一档：第二组新版第 1 轮 1000/s（磁盘卡顿 28 秒）。消费者在 `SeckillConsumer.consume()` 里先调 `tryMarkConsuming()`（第 62、131 行），它在 try 之外；连接池 2 秒借不到连接时 `CannotGetJdbcConnectionException` 直接抛出监听器（日志 11 次 `Execution of Rabbit message listener failed`），MANUAL 确认模式下这条投递既不 ACK 也不 NACK，留在通道里 unacked；库里状态停在 SENT，`cap-step.sh` 等满 600 秒也追不平。18:41 查到 7 条停在 SENT、队列 unacked 6；最终 1 条被消费，6 条被排队超时任务改成 TIMEOUT，即库存已预扣、用户最终看到失败。证据：该轮目录下的 `*-stuck-r1000.txt`、`*-stuck-r1000-queue.txt`、`*-r1000-app.log.gz`。
- 同一档另有 2 条消息因消费事务开不出连接（`CannotCreateTransactionException`，不属于 `TransientDataAccessException`）被直接判 DEAD，等人工回放。
- 这两处都在消费者代码里，PR #2 没有改动，deb719a 是同一段代码，所以是既有缺陷，只在连接池饥饿时触发。deb719a 的失败档 verify 时也有 unacked（第一组第 1 轮 1000/s 37 条、第二组第 2 轮 2000/s 30 条），但那两档没有保留应用日志、verify 又在追平前，不能确认是卡住还是正在消费。15:47 进度条目已按语义推断过这个风险，本轮在新版上实测复现。
