# 后续优化边界

本文把“已经实现”“当前证据能证明”“生产级仍需补齐”分开，避免把项目演示能力包装成线上承载能力。

## 已经实现

### 入口与并发控制

- 活动状态、短 TTL token、隐藏下单 path、库存倍数资格池。
- 可选 JWT 用户绑定与数学验证码。
- Redis ZSET 滑动窗口限流，固定窗口可回退。
- 动态规则短 TTL 缓存，包含“无规则”负缓存。
- 默认不信任 X-Forwarded-For；即使显式开启，也只有直连来源命中 `trusted-proxies` 时才解析转发头。Nginx Compose 场景已固定 edge IP 并收窄到该精确地址，生产部署应同步按实际代理地址配置。

### 库存与幂等

- Redis 用户 SKU 幂等 + MySQL 联合唯一索引。
- Redis 分片库存单 Lua 扣减；Cluster 配置回退逐桶路径。
- MySQL 分段库存与 `available_stock > 0` 条件更新。
- 删除未参与条件判断的 `sku_stock.version` 字段。
- 排队超时后释放用户 SKU 幂等 key。

### 订单与消息

- 41+10+12 位雪花订单 ID，多实例 workerId 可配置。
- 本地消息表、RabbitMQ confirm/return、退避重试、DEAD、回放。
- `CONSUMING` 状态与租约恢复，避免处理中永久悬挂。
- 瞬时数据访问异常回到重试链路；确定性库存失败记录 FAILED 订单。
- 高频观察日志使用有界线程池异步写，可回退同步。
- 订单查询只依赖订单表、Redis 精确状态和幂等 key，不依赖日志字符串。

### 工程与证据

- Swagger/OpenAPI、RequestId、Actuator/Micrometer。
- Nginx、多实例、Prometheus/Grafana Compose 示例。
- JUnit、MockMvc、Luaj、Testcontainers、JaCoCo。
- GitHub Actions 校验单测、IT、Compose 和压测证据。
- Mac ARM64 同机同参三轮优化对比报告及稳定证据目录。

## 当前证据能证明

- 三个主压测场景的三轮中位数系统错误率为 0。
- 数据库成功订单未超过初始库存，重复订单组为 0。
- 不同用户和重复请求场景的成功入队 p95 分别下降 32.8% 和 39.9%。
- 售罄尾部整体 HTTP p99 下降 87.7%。
- 动态规则负缓存和 Redis-first 查重显著减少 MySQL 查询。
- 同 jar 开关对照证明高频日志异步化降低入口尾延迟。
- 并发 Redis 扣减和 MySQL Mapper 有真实容器 IT，CI 会断言 IT 未被跳过。

## 当前不能宣传

- 10 万 QPS、百万并发。
- 生产集群容量或线性扩容倍数。
- Redis 无感恢复、任意故障全自动恢复。
- 消息绝不丢、全链路强一致。
- 入口永远恰好只受理库存数量。
- 单机 Redis 结果可直接代表 Redis Cluster。

## P1：测试继续加深

- RabbitMQ Testcontainers：confirm、return、重复投递、消费者宕机和死信回放。
- 完整下单链路 IT：真实 Redis + RabbitMQ + MySQL 组合验证。
- 滑动窗口多实例时钟偏差测试；生产实现可改用 Redis `TIME`。
- 雪花算法跨 workerId、时钟回拨和长时间压力测试。
- 库存对账与汇总视图同步窗口的专项测试。
- 故障注入：数据库死锁、连接池耗尽、MQ 不可路由、Redis 主从切换。

## P2：入口安全生产化

- 用户表、密码哈希、刷新 token、注销和 token 黑名单。
- RBAC、管理操作审计表和回放审批流。
- 网关层强制隐藏 path、设备指纹、黑名单和风险评分。
- 图片/滑块验证码与限流策略平台。
- 可信代理网段支持标准 CIDR 解析，而不是简化前缀匹配。

## P3：可观测性和运维

- 持续采集 CPU、GC、线程池、连接池、慢 SQL、Redis 命令和 MQ 延迟时序。
- 为异步日志拒绝、消息重试耗尽、CONSUMING 租约恢复、库存对账修复设置告警阈值。
- 把 requestId 贯穿 MQ header、消费者、订单、补偿和回放批次。
- Grafana dashboard 通过实际演练校准，不只保留示例 JSON。
- 增加 runbook：Redis 恢复、死信回放、库存不一致和 workerId 冲突。

## P4：分布式容量与高可用

- Redis Cluster 重新设计 hash tag，评估多 key Lua 与分片能力的取舍。
- RabbitMQ quorum queue、集群拓扑、publisher confirms 和容量水位。
- MySQL 主从、读写分离、分库分表或按活动分片。
- 多机压测和网络隔离故障测试，不再只看单机容器。
- workerId 由注册中心或部署编排统一分配，避免人工配置重复。

## P5：业务完整度

- 商品和活动后台、审批与灰度。
- 支付、取消、退款、超时关闭和库存回补。
- 用户通知、前端轮询或 WebSocket 状态推送。
- 订单状态与支付状态的更完整状态机。

## 推荐面试说法

> 这个项目已经把秒杀主链路、可靠消息、恢复和真实压测证据做成了可运行闭环，但我不会把它说成生产级系统。当前最值得继续补的是 RabbitMQ 与完整链路 Testcontainers、持续性能时序和故障注入；再往后才是网关风控、真实集群和分库分表。
