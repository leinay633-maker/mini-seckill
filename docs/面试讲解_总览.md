# 面试讲解总览

## 一分钟版本

我做的是一个聚焦秒杀下单链路的 Java 后端项目，不是完整商城。用户先获取短 TTL token 和隐藏下单 path，下单时依次经过活动校验、Redis ZSET 滑动窗口限流、token 原子消费、用户 SKU 幂等和 Redis 分片库存单 Lua 扣减。抢到资格后先写本地消息表，再投递 RabbitMQ；消费者在 MySQL 事务里创建订单并执行 `available_stock > 0` 条件扣减，最后由重试、`CONSUMING` 租约恢复、超时、对账和 Redis 恢复把异常链路收敛。

项目里我重点修了几个真实问题：订单号改为 41+10+12 位雪花算法，多实例 workerId 可配置；动态规则支持“无规则”负缓存；token 热路径改为 Redis-first；高频业务日志改成有界线程池异步写；分片库存从多次 Redis 往返收敛为单次 Lua；超时关单会释放幂等 key；删除了从未参与条件判断的假 `version` 字段。

我用同一台 Apple M1 Mac 做了优化前后同参压测。不同用户场景成功入队 p95 从 8.17 ms 降到 5.49 ms，重复请求场景从 7.92 ms 降到 4.76 ms，售罄尾部整体 HTTP p99 从 98.27 ms 降到 12.04 ms。所有主场景三轮中位数系统错误率为 0，数据库成功订单不超过库存，重复订单组为 0。

边界也要说清楚：这是单机可复现证据，不是 10 万 QPS 或生产集群容量证明；入口返回“排队中”不等于最终成功，最终状态要查订单。

## 三分钟版本

### 1. 入口为什么分两步

用户先请求 `/api/seckill/token`，服务端检查活动、售罄状态和是否已有订单/排队事实，再生成短 TTL token 与隐藏 path。token 资格池默认按库存倍数发放，避免无限请求都进入真正下单链路。可选 JWT 和数学验证码用于演示用户绑定与基础防刷，默认可关闭以保持压测口径可控。

### 2. 下单入口怎么抗并发

下单默认使用 Redis ZSET 滑动窗口，按活动 SKU、用户和 IP 三个维度限流；保留固定窗口开关便于回退。token 用 Lua compare-and-delete 原子消费，随后用 Redis `SET NX` 写用户 SKU 幂等 key。

库存默认分成 64 个 bucket。单机 Redis 下把全部 bucket 作为一次 Lua 的 KEYS 传入，脚本从用户 hash 对应位置环形扫描并原子扣减，因此一次请求只需要一次 Redis 往返；Redis Cluster 下因为跨 slot 限制，配置会关闭单 Lua并回退兼容路径。

### 3. 为什么还要 MQ 和 MySQL

Redis 扣成功后，入口同步写本地消息事实并投递 RabbitMQ，然后返回“排队中”。高频观察日志通过有界线程池异步写，避免日志占用请求线程和数据库连接；本地消息仍同步落库，因为它是可靠性事实，不能用异步日志替代。

消费者先把消息 CAS 到 `CONSUMING`，再在 MySQL 事务里插入订单并扣库存。数据库用联合唯一索引防重复，用 `available_stock > 0` 条件更新防超卖。`sku_stock.version` 已删除，因为旧代码只自增它，从未在 `WHERE` 中比较，不构成乐观锁。

订单 ID 使用雪花算法：41 位时间戳、10 位 workerId、12 位序列。多实例通过 `MINI_SECKILL_WORKER_ID` 分配不同 workerId，避免旧毫秒序列算法在多实例同毫秒撞号。

### 4. 异常怎么收敛

- MQ 发送失败：本地消息状态进入可重试分支，后台退避重投。
- 消费瞬时数据访问异常：从 `CONSUMING` 回到失败状态，由重试任务接管，不直接当永久死信。
- 确定性 MySQL 库存失败：记录 FAILED 订单，保证用户结果长期可查。
- 消费者在 `CONSUMING` 后崩溃：租约恢复任务按订单事实补成 CONSUMED 或回退重试。
- 排队超时：写 TIMEOUT 后删除用户 SKU 幂等 key，闭合 10 分钟超时与 30 分钟幂等 TTL 的语义。
- Redis 故障：入口 fail-closed，恢复时按 `MySQL 可用库存 - 未完成消息数` 重建 Redis 库存。

## 十分钟展开顺序

1. 先画“准入 → Redis 原子扣减 → 本地消息 → MQ → MySQL 事实 → 恢复任务”主链路。
2. 用三层正确性解释防超卖：Redis Lua、MySQL 条件更新、订单唯一约束。
3. 用消息状态机解释可靠性：SENDING、SENT、CONSUMING、CONSUMED、FAILED、TIMEOUT、DEAD。
4. 用 D2/D3/D4/A3 解释性能优化：减少 MySQL 查询、异步非关键日志、减少 Redis RTT。
5. 用真实数字证明优化，但主动说明单机、三轮中位数、跨机器不可比。
6. 最后讲生产边界：真实风控、网关、MQ 集群、Redis 高可用、多机压测、分库分表和告警值班仍未覆盖。

## 推荐演示顺序

1. 打开 Swagger UI，展示 Auth、Captcha、Seckill、Order、Admin、Activity、Recovery 分组。
2. 初始化库存并获取 token/orderPath。
3. 使用隐藏 path 下单，观察 HTTP 200 + body `code=0` 的排队语义。
4. 轮询订单，展示最终 SUCCESS 或 FAILED 事实。
5. 打开 `REPORT.md` 和 `benchmark/evidence/mac-arm64/`，解释同机对比和证据边界。
6. 运行 `mvn -B clean verify` 与 `mvn -B clean -Pintegration-test verify`，展示测试和 JaCoCo。
