## 1. 项目一句话介绍

Mini秒杀项目是一个个人实现的高并发秒杀下单样板项目，核心是用活动状态控制入口，用库存倍数短 TTL token 控制入口资格，用 Redis Lua 做限流和热点库存原子扣减，用 Set-N-X 和 MySQL 联合唯一索引防重复下单，用 RabbitMQ 异步削峰，最后用 MySQL 事务保证订单和库存的最终事实。现在项目还补了库存预热、Redis 库存分片、本地消息表、RabbitMQ confirm、排队超时、自动对账任务和 Redis 宕机恢复入口，但定位仍然是个人项目，不会吹成生产级系统。

## 2. 30 秒项目介绍

我这个项目叫 Mini秒杀项目，是一个聚焦秒杀下单链路的 Java 后端项目，不是完整电商系统。它主要解决三个问题：高并发下库存不能超卖，同一个用户不能重复下单，以及瞬时流量不能直接打到 MySQL。我的做法是先用库存倍数 token 资格池挡掉大部分无资格请求，再做 Redis Lua 限流和 Redis Set-N-X 用户维度幂等校验，然后用 Redis Lua 原子扣减热点库存。扣减成功后先写本地消息表，再投递 RabbitMQ，接口先返回排队中。消费者异步消费消息，在一个 MySQL 事务里插入订单和扣减库存，数据库层再用 User ID 加 SKU ID 的联合唯一索引和“可用库存大于 0”做兜底。

## 3. 1 分钟项目介绍

Mini秒杀系统是我为服务端研发面试准备的一个高并发秒杀订单系统，重点不是商品、支付这些电商外围功能，而是下单链路本身。用户请求进入后，先经过短 TTL token 资格池，项目默认按库存的倍数发 token，资格发完后请求在入口阶段快速失败。真正下单时，我再做 Redis Lua 限流，用 Redis Set-N-X 写用户加商品维度的幂等 key，挡住重复点击、超时重试和重复提交。接着用 Redis Lua 脚本对活动 SKU 库存分片做原子扣减，避免 `GET` 再 `DECR` 之间出现并发窗口。扣减成功后不会同步写 MySQL，而是先落一条本地消息记录，再发送 RabbitMQ 消息，接口快速返回“排队中”。消费者端开启 MySQL 事务，插入订单并执行带“可用库存大于 0”条件的库存扣减 SQL，同时订单表有 U-K User Sku 联合索引作为最终幂等兜底。

## 4. 2 分钟项目介绍

Mini秒杀系统是一个个人项目，设计参考真实高并发秒杀场景，但没有宣称生产级上线。我的目标是把服务端研发最常见的高并发问题集中到一条下单链路里：活动状态、动态 token、防刷限流、热点库存、重复请求、异步削峰、数据库事务、最终一致性和异常补偿。系统提供活动管理、初始化库存、库存预热、获取 token、秒杀下单、查询订单和查询库存接口，技术栈是 Java 17、Spring Boot 3、MyBatis、MySQL 8、Redis、RabbitMQ、Docker Compose，并补了 Nginx 示例和 k6 压测脚本。

核心流程是这样的：初始化和预热时先拿 Redisson 的活动 SKU 级分布式锁，再把库存同步到 MySQL、Redis 总库存 key、Redis 分片库存 key 和 token 资格池 key，避免多个实例同时重置同一个活动库存；下单前用户先获取短 TTL token，token 总量默认按库存倍数控制；下单时先做 Redis Lua 限流，再校验 token 和 Set-N-X 幂等 key；然后执行 Redis Lua 脚本扣某个库存分片，库存不存在返回 -1，库存不足返回 0，扣减成功返回 1。只有 Lua 扣减成功的请求才会写本地消息表并发送 RabbitMQ 消息，接口快速返回排队中，这样 MySQL 不会被瞬时流量直接打满。消费者消费消息时开启事务，先插入订单，再执行带“可用库存大于 0”条件的库存扣减 SQL，如果库存已经不足就回滚事务。

这个项目有两个幂等层：入口层用 Redis Set-N-X 减少重复请求进入 MQ，数据库层用活动 ID 加 User ID 加 SKU ID 的联合唯一索引防止重复订单成为事实。它也有两个库存层：Redis 是高并发入口库存，MySQL 是最终事实库存，其中 Redis 侧还做了 bucket 分片来降低单 key 压力。异常方面，如果 MQ 发送失败，请求已经写入本地消息表，confirm 或 return 回调会更新状态，后台任务可以继续重投；如果消费失败，会走手动 ACK、NACK、死信队列和消息状态标记；如果 Redis 宕机或库存 key 丢失，系统会先进入恢复态暂停入口，再按 MySQL 可用库存减未完成消息数重建 Redis 库存。面试讲这个项目时，我会强调自己没有做完整电商，而是把范围收敛到服务端高并发链路。

## 5. 项目背景与岗位匹配

拼多多服务端研发岗位关注高并发、高流量、分布式、高可用、高可靠、高扩展、数据库和基础工程能力。秒杀下单是一个很适合作为个人项目的场景，因为它天然包含热点访问、库存竞争、重复请求、异步处理和数据库一致性问题。这个项目没有做前端、登录、支付和优惠券，是为了避免范围发散，把时间集中在服务端链路设计上。

和岗位匹配的点主要有五个。第一是 Spring Boot 服务端工程能力，项目有 Controller、Service、Mapper、配置、MQ、统一返回和异常处理。第二是高并发入口处理能力，Redis 承接热点库存，Lua 保证原子扣减和限流。第三是可靠性设计，Set-N-X、联合唯一索引、事务、条件更新、本地消息表和 MQ 手动 ACK 都是为了避免脏数据。第四是异步架构能力，RabbitMQ 用来削峰填谷，让接口和数据库写入解耦。第五是面试可讲性强，可以从代码落到 Redis、MySQL、MQ、Java 并发、操作系统、网络和算法基础。

## 6. 系统架构

```text
用户请求
  |
  v
Spring Boot API
  |
        +-- 初始化/预热库存 -> MySQL 库存表 + Redis 活动库存 key
  |
  +-- 秒杀下单
        |
        +-- 参数校验
        +-- 库存倍数 token 资格池
        +-- Redis Lua 限流
        +-- Redis Set-N-X 幂等 key
        +-- Redis Lua 原子扣活动库存
        +-- 写本地消息表
        +-- RabbitMQ 发送下单消息
        +-- 接口返回排队中
              |
              v
          MQ Consumer
              |
              +-- MySQL 事务
              +-- 插入 seckill_order
              +-- 条件扣减 sku_stock
              +-- 写 seckill_log
              +-- 更新 seckill_message

  +-- Redis 故障恢复
        |
        +-- 健康检查连续失败后进入恢复态
        +-- token 和下单入口 fail closed
        +-- Redis 重启后按 MySQL 可用库存 - 未完成消息数重建库存
```

这套架构的职责划分很清楚。token 资格池负责第一层削流，避免所有人都进入真正下单链路。Redis 负责高并发入口，解决热点库存、重复点击和服务端限流问题。RabbitMQ 负责异步削峰，把瞬时请求变成可控的消费速率。MySQL 负责最终事实，订单和库存的真实结果必须落在数据库事务里。本地消息表负责让“Redis 扣成功但 MQ 投递失败”的请求可恢复。Redis 宕机恢复这里我没有假装做强一致，而是让入口先关住，再从 MySQL 和本地消息表恢复 Redis 入场库存。

## 7. 核心下单链路

核心链路可以概括为“先限流，再挡重复，再扣热点库存，再异步落库，最后数据库兜底”。请求进入 `POST /api/seckill/order` 后，先校验 `activityId`、`userId` 和 `skuId`，然后做 Redis Lua 固定窗口限流。通过限流后，用 Redis Set-N-X 设置用户维度幂等 key。如果这个 key 已存在，说明用户已经下过单或者正在排队，直接返回重复请求。通过幂等校验后，执行 Lua 脚本扣 Redis 活动库存，只有返回 1 才说明抢到入口资格。接着写本地消息表并发送 RabbitMQ 消息，消费者异步创建订单，并在 MySQL 事务里扣库存。

这个链路的关键不是单个组件，而是每一层各司其职。Redis 不直接代表最终订单，只负责入口限流和热点库存。MQ 不负责业务正确性，只负责削峰和解耦。MySQL 不承接全部并发，但负责最后的数据正确性。这样设计的好处是高并发场景下先保护数据库，同时又不把正确性完全寄托在缓存上。

## 8. Redis Lua 库存扣减

Lua 脚本的语义是：库存 key 不存在返回 -1，库存小于等于 0 返回 0，库存大于 0 就执行 `DECR` 并返回 1。为什么不用 Java 里先 `GET` 再 `DECR`，是因为这两个命令中间有并发窗口。多个请求可能同时读到库存大于 0，然后都去扣减，最终出现负库存。Lua 在 Redis 内部作为一个脚本执行，Redis 执行脚本期间不会插入其他命令，所以判断和扣减是一个原子动作。这个项目把 Lua 放在 `src/main/resources/lua/seckill_stock.lua`，便于面试时直接展示。

## 9. Redis SETNX 幂等防重

Set-N-X 的作用是给“活动 + 用户 + 商品”建立一个入口凭证。key 是 `seckill:user:{activityId}:{userId}:sku:{skuId}`，如果第一次请求设置成功，就允许继续扣库存和发 MQ；如果设置失败，说明同一用户已经请求过这个活动商品，直接返回重复下单或排队中。这个设计能处理用户连续点击、HTTP 超时重试、前端重复提交等常见问题。Set-N-X 不是唯一兜底，因为 Redis key 可能过期或丢失，所以数据库里还有活动 ID、User ID 和 SKU ID 的联合唯一索引。入口防重减少无效流量，数据库唯一索引保证最终不会生成重复订单。

## 9.1 Redisson 分布式锁边界

这个项目实现了 Redisson 分布式锁，但我不会用它替代 Redis Lua 做热点库存扣减。分布式锁适合保护一段跨资源临界区，比如库存初始化、库存预热或对账修正时，需要同时考虑 MySQL 事实表和 Redis 库存 key。项目里用活动 SKU 维度锁，避免多个服务实例同时初始化或修正同一个活动库存。下单扣库存走的是 Redis Lua，因为它把判断和扣减合成一个 Redis 内部原子动作，少了加锁、释放锁和锁超时问题。面试可以直接说：有分布式锁能力，但我把它放在低频管理动作上，热点扣库存仍然用 Lua。

## 10. MySQL 表设计、事务、索引

项目核心有四张表：库存事实表、订单事实表、请求日志表和本地消息表。库存事实表按活动 ID 和 SKU ID 做唯一约束，订单事实表最重要的是活动 ID、User ID 和 SKU ID 的联合唯一索引，它保证一个用户对同一个活动商品最多只有一条订单。本地消息表记录请求是否待发送、已发送、已消费或发送失败，给 MQ 投递失败提供可恢复入口。消费者创建订单时用一个 MySQL 事务，订单插入和库存扣减必须一起成功或一起回滚。库存扣减 SQL 带“可用库存大于 0”条件，这是数据库层防止扣成负数的最后防线。

## 11. RabbitMQ 异步削峰

RabbitMQ 的作用是把接口流量和数据库写入解耦。秒杀请求瞬时进来，如果每个请求都同步写 MySQL，数据库连接池、行锁和磁盘 IO 很容易被打满。使用 MQ 后，接口只完成 Redis 校验、本地消息记录和消息投递，然后快速返回“排队中”。消费者按可控并发慢慢写 MySQL，这样数据库看到的是相对平滑的流量。项目里保留了交换机、队列、死信队列、JSON 消息、手动 ACK 和消息重投任务，方便说明可靠消息如何继续扩展。

## 12. MQ 重复消费与幂等

MQ 重复消费是正常现象，不能假设消息只会被消费一次。这个项目的处理方式是让业务天然幂等：订单表对活动 ID、User ID 和 SKU ID 建联合唯一索引。消费者如果重复收到同一用户同一活动商品的消息，插入订单时会触发 `DuplicateKeyException`，这时认为之前已经处理过，直接 ACK，不再重复扣库存。本地消息表也会把这类消息标记成已消费。这样做比单纯依赖消费端内存去重可靠，因为服务重启、并发消费和多实例部署都会让内存状态不可信。

## 13. Redis 和 MySQL 一致性

这个项目里 Redis 和 MySQL 的职责不同。Redis 是入口库存，用来抗高并发；MySQL 是最终事实，用来记录真实库存和订单。正常情况下，Redis 先扣库存，MQ 消费后 MySQL 再扣库存，两者短时间内可能不一致，但最终应该收敛。异常情况下，比如 MQ 发送失败，本地消息表会留下待补偿记录，由定时任务继续重投；如果消费失败，消息会进入死信队列或等待补偿。Redis 宕机恢复时不能直接把 Redis 写成 MySQL 可用库存，因为还有一批 Redis 已经扣成功、但 MySQL 还没消费完成的排队消息。项目里的恢复公式是“Redis 入场库存 = max(0, MySQL 可用库存 - 未完成消息数)”，这样能避免 Redis 重启后重复释放这批入口资格。

## 14. 异常场景与补偿方案

异常要分阶段看。第一类是 Redis 库存不存在或不足，这类请求不进入 MQ，删除幂等 key 后直接返回失败。第二类是 Redis 扣减成功但 MQ 发送失败，项目里不会直接丢请求，而是把本地消息表标记为失败，由定时任务后续重投。第三类是 MQ 消费失败，未知异常会 NACK 并进入死信队列，同时记录失败状态。第四类是 MySQL 唯一索引冲突，说明重复消费或重复下单，直接 ACK，并把消息标记为已消费。第五类是 Redis 宕机或 key 丢失，健康检查会把入口切到恢复态，token 和下单接口返回 503，Redis 重启后再执行恢复接口重建总库存和 bucket 分片库存。

## 15. 压测方案

压测重点不是追求夸张 QPS，而是验证链路正确性。第一组测试是单活动单 SKU 库存 100，并发 500 或 1000，请求结束后检查成功订单数不能超过 100，MySQL 可用库存不能小于 0。第二组测试是同一个用户重复请求 100 次，验证最终只生成一条订单。第三组测试是暂停或降低消费者速度，观察接口是否仍能快速返回排队中，同时 RabbitMQ 队列出现可解释的积压。第四组测试是模拟 MQ 不可用，验证本地消息表是否能保留待重投记录。第五组是 10 万 VU 涌入脚本，重点看大量请求是否在 token、限流和 Redis 层快速失败，而不是把它们都送进 MySQL。

## 16. 项目不足与生产级改进

这个项目是个人项目简化版，不是生产级系统。当前已经补了活动维度、库存倍数 token 资格池、服务端 Lua 限流、库存预热、Redis 库存分片、Redis Cluster 本地演示、本地消息表、RabbitMQ confirm/return、消息重投、排队超时、库存对账任务、Redis 宕机恢复入口和 10 万用户涌入压测脚本，但没有登录鉴权、完整风控、验证码、完整监控和生产级补偿后台。生产级首先要在网关层做限流和风控，减少异常流量进入业务服务。其次要增强 MQ 可靠性，比如更完整的消息状态机、死信队列告警和人工补偿入口。再次要提升库存体系，比如云上 Redis Cluster、更细粒度库存分片、热点 key 拆分、全量分页预热和恢复进度表。最后还要补齐可观测性，至少要有 QPS、延迟、错误率、队列积压、消费延迟、Redis 命中和 MySQL 慢 SQL 指标。

验收标注：当前代码里的活动状态机、短 TTL token、token 资格池、Redis Set-N-X、Redis Lua 扣库存、Redis Lua 限流、Redis 库存分片、RabbitMQ confirm/return、RabbitMQ 投递与消费、本地消息表、MySQL 事务、唯一索引兜底、库存预热、Redis 恢复态、恢复接口、排队超时和对账任务都是真实实现，不是伪代码。简化点主要有三处：第一，MQ 可靠消息虽然接了 confirm 和 return，但还没有生产级告警后台和人工重放页面。第二，Redis 恢复和对账是个人项目版，扫描范围按配置上限处理，没有做恢复进度表、工单和人工确认后台。第三，风控、验证码和完整网关治理没有接入真实组件；面试可以说“项目范围有意收敛到下单主链路，这些是生产级扩展项，不虚构上线经历”。

## 17. 拼多多服务端岗位匹配回答

如果面试官问这个项目为什么匹配服务端研发，我会先说结论：它覆盖了服务端高并发链路里最核心的几个问题。拼多多这类业务有高流量、高并发、强工程效率和成本意识，所以不能只会写 CRUD，还要能解释请求峰值、缓存、队列、数据库和异常恢复。Mini秒杀项目虽然是个人项目，但我有意识地把它设计成“入口抗并发、队列削峰、数据库兜底、异常可补偿”的结构。Redis Lua 体现对原子性和热点数据的理解，RabbitMQ 和本地消息表体现异步可靠性设计，MySQL 事务和唯一索引体现数据正确性意识。项目不足我也会主动说明，比如没有生产级风控和完整监控，但我能讲清楚怎么扩展。

## 18. 项目追问 QA，至少 50 个

### Q1. 你这个项目是做什么的？

答：它是一个个人实现的高并发秒杀下单系统，重点是服务端下单链路，不是完整电商。项目解决的是库存不能超卖、用户不能重复下单、数据库不能被瞬时流量打穿这三个问题。技术上用了 Spring Boot、Redis、RabbitMQ 和 MySQL。Redis 负责入口库存和幂等，MQ 负责削峰，MySQL 负责最终订单和库存事实。面试时我会把它讲成一个服务端高并发链路样板。

### Q2. 为什么选秒杀系统？

答：秒杀系统是一个很适合服务端研发面试的场景，因为问题集中而且边界清楚。它天然有高并发、热点 key、重复请求、异步削峰、数据库事务和一致性问题。相比做完整商城，秒杀可以把技术重点放在后端核心链路上。这个项目没有做登录、支付和优惠券，就是为了避免功能分散。对拼多多服务端岗位来说，这类链路也更贴近高流量业务。

### Q3. 为什么这个项目适合服务端研发？

答：因为它不只是接口 CRUD，而是围绕高并发下单做架构取舍。项目里有缓存、消息队列、数据库事务、唯一索引、幂等、异常补偿和压测思路。这些都是服务端研发日常会遇到的基础工程问题。即使项目规模不大，也能体现我对后端链路稳定性的理解。它更适合讲能力，而不是堆功能。

### Q4. 你的核心链路是什么？

答：核心链路是参数校验、库存倍数 token 资格池、Redis Lua 限流、Redis Set-N-X 幂等、Redis Lua 扣库存、写本地消息表、发送 RabbitMQ、消费者异步落库。接口不直接写 MySQL，而是先返回排队中。消费者在 MySQL 事务里插入订单并扣库存。数据库用联合唯一索引和条件更新做最终兜底。这个链路体现的是先筛资格、再控流量、再抗并发、再削峰、最后保证事实正确。

### Q5. 这个项目最大难点是什么？

答：最大难点不是写接口，而是多层状态的一致性。Redis 先扣库存，MQ 后写数据库，中间任何一步失败都可能导致状态不一致。所以要设计幂等、补偿和数据库兜底。比如 MQ 发送失败要恢复 Redis，重复消费要靠唯一索引兜底，MySQL 扣库存要带条件。这个项目的重点就是把这些异常路径想清楚。

### Q6. 你怎么防止超卖？

答：我用了两层防超卖。第一层是在 Redis 用 Lua 脚本原子判断库存并扣减，避免高并发入口超卖。第二层是在 MySQL 扣库存 SQL 里加“可用库存大于 0”，避免数据库层扣成负数。Redis 主要负责抗流量，MySQL 负责最终事实。即使 Redis 状态短暂异常，MySQL 条件更新也能做最后防线。

### Q7. 你怎么防止重复下单？

答：我用了三层防重复。第一层是短 TTL token，同一个 token 下单后会删除，降低重放风险。第二层是入口层 Redis Set-N-X，写活动、用户、商品维度的幂等 key，同一用户同一活动商品只能第一次设置成功。第三层是数据库层活动 ID 加 User ID 加 SKU ID 的联合唯一索引兜底。Set-N-X 可以减少重复请求进入 MQ，唯一索引保证重复订单不会成为最终事实。这样即使 MQ 重复消费，也不会插入两条订单。

### Q8. 为什么要用 Redis？

答：因为秒杀库存是典型热点数据，如果所有请求都直接查 MySQL，数据库压力会很大。Redis 是内存数据库，单次操作延迟低，适合承接高频库存扣减。这里 Redis 不是最终事实，而是入口层的高并发库存。它把大部分无效请求挡在数据库之前。最终结果仍然以 MySQL 订单和库存为准。

### Q9. 为什么要用 MQ？

答：MQ 的核心作用是削峰和解耦。秒杀请求是瞬时高峰，如果同步写数据库，连接池和行锁会承受很大压力。使用 RabbitMQ 后，接口只负责抢资格和投递消息，数据库写入由消费者按可控速度完成。这样用户侧响应更快，数据库侧压力更平滑。代价是系统变成最终一致，需要处理消息丢失、重复和积压。

### Q10. 为什么还要 MySQL？

答：Redis 适合高并发入口，但不适合作为订单和库存的最终事实。订单数据需要持久化、事务、索引和可查询能力，这些是 MySQL 更擅长的。MySQL 里有订单唯一索引和库存条件更新，可以做最终兜底。Redis 扣成功只能说明用户拿到入口资格，不代表订单已经最终成功。最终成功要看 MySQL 事务是否提交。

### Q11. Redis 和 MySQL 谁是最终事实？

答：MySQL 是最终事实。Redis 只是高并发入口状态，用来快速判断库存和防重复请求。因为 Redis 可能过期、重启、主从切换或者和 MQ 链路产生短暂不一致。订单是否成功、库存最终剩多少，应该以 MySQL 订单表和库存表为准。生产级系统会用对账任务把 Redis 修正到和 MySQL 一致。

### Q12. 项目有哪些不足？

答：这个项目是个人项目简化版，范围有意收敛。它没有登录鉴权、完整风控、验证码、支付、优惠券和复杂订单状态。可靠消息已经有本地消息表、confirm/return 回调和重投任务，但没有生产级告警、人工重放后台和完整消息运营页面。Redis 恢复已经有健康检查、入口恢复态和库存重建接口，但没有做全量恢复进度表、工单审批和多机恢复编排。面试中我会主动说明这些不足，并讲生产级扩展方向。

### Q13. 如果生产级部署你会怎么改？

答：生产级我会先加网关限流、风控和验证码，把异常流量挡在业务服务之前。然后把 Redis 做成高可用集群，并把当前简化版库存分片扩展成更完整的库存分段和归并方案。Redis 恢复这块要接 Sentinel 或 Cluster 事件、恢复进度表、全量分页预热和人工确认开关，不能靠一个接口粗暴放开。MQ 侧当前已经有本地消息表和 confirm/return，生产级还要补告警、人工重放后台和更完整的消息状态机。MySQL 侧要做读写分离、分库分表、慢 SQL 和锁等待监控。

### Q14. Redis 挂了怎么办？

答：Redis 挂了会影响入口库存、限流、token 和 Set-N-X 幂等校验，不能简单继续放流量打 MySQL。项目里做法是健康检查连续失败后进入恢复态，token 和下单接口直接返回 503，相当于秒杀入口 fail closed。Redis 重启后不能立刻继续卖，因为库存 key 可能丢了，必须先执行恢复接口重建库存。恢复公式不是简单写 MySQL 可用库存，而是 MySQL 可用库存减掉未完成 MQ 消息数。生产级还要用 Redis 主从、哨兵或 Cluster 降低故障概率，并把恢复过程接到监控和人工确认。

### Q14.1 Redis 宕机后怎么恢复库存？

答：先给结论：不能直接把 Redis 库存刷成 MySQL 可用库存，要先扣掉还在排队或待重试的消息数。因为这些消息已经在 Redis 入口扣过库存，只是 MySQL 还没最终消费完成。如果 Redis 重启后不扣这部分，就会把同一批入口资格又释放出去，容易造成后续少量超卖压力。项目里的恢复公式是 `max(0, MySQL 可用库存 - 未完成消息数)`，然后同时重建总库存 key 和 bucket 分片 key。恢复期间 token 和下单入口是关闭的，恢复完成后才放开入口。

### Q15. MQ 挂了怎么办？

答：MQ 挂了说明请求即使抢到 Redis 库存，也可能暂时无法异步落库。项目里如果发送失败，会把本地消息表标记为失败，后台任务继续补发，所以不会直接吞掉这次抢资格结果。生产级还要加 publisher confirm 和 return callback，确认消息是否真的到 Broker。也可以短时间开启同步 fallback，但要严格限流，不能让 MySQL 被打穿。核心原则是不能吞消息，也不能让用户状态永久卡住。

### Q16. MySQL 压力过大怎么办？

答：先要确认压力来源，是连接池满、慢 SQL、锁等待还是磁盘 IO。这个项目通过 Redis 和 MQ 已经减少了 MySQL 的瞬时压力。生产级可以降低消费者并发、增加队列积压承受能力、做读写分离和分库分表。库存更新是热点写，必要时可以做库存分段或异步汇总。最重要的是不要在请求入口同步打 MySQL。

### Q17. 怎么做限流？

答：限流应该尽量前置，比如网关层按 IP、用户、SKU 和活动维度限流。算法上可以用令牌桶、漏桶或滑动窗口。这个项目做了两层简化：Nginx 配置里给了前置限流示例，业务服务里用 Redis Lua 做固定窗口限流。限流不是为了让所有请求成功，而是为了保护系统在高峰时可控失败。生产级还会加风控、验证码和黑名单。

### Q18. 怎么做降级？

答：降级要分依赖来做。Redis 不可用时，可以暂停秒杀或进入只读状态。MQ 不可用时，可以回滚 Redis 抢占结果并提示稍后重试。MySQL 压力过大时，可以降低消费者并发，让请求继续排队但不继续压数据库。降级的目标是保护核心数据正确，而不是强行保证所有请求成功。

### Q19. 怎么做监控？

答：监控至少要覆盖接口、Redis、MQ、MySQL 和业务指标。接口看 QPS、P95/P99 延迟和错误率。Redis 看命令耗时、连接数、内存、热 key 和 Lua 执行失败。MQ 看队列积压、消费速率、消费失败和死信数量。MySQL 看连接池、慢 SQL、锁等待、TPS 和库存扣减影响行数。

### Q20. 怎么做压测？

答：压测不只看吞吐量，还要看数据正确性。可以初始化库存 100，然后并发 500 请求下单，最后检查订单数不能超过 100。再用同一个用户重复请求，确认只有一条订单。还要测试消费者变慢时队列是否积压，以及接口是否仍能快速返回排队中。压测结论要用 SQL 和队列指标证明，而不是只看接口返回。

### Q21. 为什么接口返回排队中而不是成功？

答：因为 Redis 扣库存成功只代表用户拿到下单资格，不代表 MySQL 订单已经创建成功。订单真正成功要等 MQ 消费者完成事务提交。如果接口直接返回成功，会误导用户，也会让后续失败很难解释。返回排队中更符合异步架构语义。用户可以通过查询订单接口看最终状态。

### Q22. 为什么先 SETNX 再 Lua 扣库存？

答：先做 Set-N-X 可以挡住同一个用户的重复请求，减少后续库存扣减和 MQ 投递压力。如果先扣库存再做幂等，重复请求可能先消耗入口库存，再发现重复，补偿会更多。Set-N-X 成功后再 Lua 扣库存，链路更清晰。库存不足或库存不存在时会删除幂等 key，避免用户被错误卡住。这个顺序是为了减少无效流量和补偿复杂度。

### Q23. SETNX 成功后 Lua 扣库存失败怎么办？

答：如果 Lua 返回库存不存在或库存不足，说明这个请求没有拿到资格。项目里会删除刚才设置的用户幂等 key，并记录日志。这样用户后续如果活动补库存，仍然有机会重试。不能保留幂等 key，否则一次失败会让用户一直处于已请求状态。这个处理属于入口阶段的轻量补偿。

### Q24. Lua 扣库存成功但 MQ 发送失败怎么办？

答：这是一个典型中间状态异常。当前项目的处理是先写本地消息表，RabbitMQ 发送失败就把消息标记为失败，后续由重试任务补发。这样 Redis 已经扣掉的入口资格不会凭空丢掉，用户查询时也能看到排队或失败状态。生产级还要配合 publisher confirm 判断消息是否真的到 Broker。这个设计比简单回滚 Redis 更接近可靠消息的思路。

### Q25. 消费者插入订单成功但扣库存失败怎么办？

答：项目里插入订单和扣 MySQL 库存在同一个事务里。如果扣库存 SQL 影响行数不是 1，就抛异常回滚事务，所以订单也不会提交。这个情况通常说明 Redis 和 MySQL 库存不一致，或者数据库库存已经被其他路径扣完。消费者会记录失败状态，消息进入失败处理路径，避免无限重试把队列打爆。对账任务后续会按 MySQL 事实库存修正 Redis，生产级还要触发告警。

### Q26. 为什么订单插入放在扣库存前？

答：这样可以让 U-K User Sku 联合索引更早拦截重复消费。如果是重复消息，插入订单会直接触发唯一索引异常，事务回滚，不会执行库存扣减。即使后续扣库存失败，插入也会因为事务回滚而撤销。也可以先扣库存再插订单，但重复消费时更依赖事务回滚。这个项目选择先插订单，是为了突出唯一索引幂等兜底。

### Q27. 为什么 MySQL 扣库存还要加条件？

答：“可用库存大于 0”是数据库层最后一道防线。即使 Redis 层已经扣过库存，也不能假设上游永远正确。条件更新能保证 MySQL 不会把库存扣成负数。影响行数为 0 就说明数据库认为库存不足，事务需要回滚。这个设计体现的是不能把正确性只放在缓存里。

### Q28. 为什么不直接用数据库锁解决库存？

答：直接用数据库锁可以保证正确性，但高并发秒杀下会让大量请求竞争同一行库存。行锁等待会导致连接池占满、响应变慢，最终拖垮数据库。这个项目让 Redis 先过滤大部分请求，只有抢到资格的消息才进入 MySQL。数据库只做最终兜底，不承接全部入口流量。这样更符合高并发下的分层设计。

### Q29. 为什么不用 synchronized？

答：`synchronized` 只能保证单 JVM 内的线程互斥。服务端部署多实例后，不同机器之间的锁互相不知道，不能保护全局库存。即使单机能工作，也无法应对分布式部署。秒杀库存是跨进程共享资源，更适合用 Redis Lua 或数据库条件更新。Java 锁可以保护本地内存状态，但不适合做全局库存扣减。

### Q30. 查询订单为什么可能先显示排队中？

答：因为下单接口是异步链路。用户请求通过 Redis 和 MQ 后，接口先返回排队中，但消费者还没有完成 MySQL 事务。这个时间窗口里订单表查不到记录，但 Redis 幂等 key 还存在，所以可以返回排队中。等消费者提交事务后，再查询就会返回成功。这是异步削峰带来的正常最终一致状态。

### Q31. seckill_log 表有什么作用？

答：`seckill_log` 是一个轻量日志表，用来记录请求经过的关键结果。它不是生产级完整审计表，但适合展示异常路径和补偿思路。比如库存不足、MQ 发送失败、重复消费、订单成功都可以留下记录。查询订单时也可以根据最近日志判断失败状态。生产级可以把它扩展成本地消息表或操作流水表。

### Q32. 你的 Docker Compose 做了什么？

答：Docker Compose 启动 MySQL 8、Redis 和 RabbitMQ management。MySQL 启动时会自动执行 `sql/init.sql` 建库建表。Redis 暴露 6379，RabbitMQ 暴露 5672 和 15672 管理界面。这样面试前本地可以一条命令拉起依赖。项目本身仍然用 Maven 启动 Spring Boot 服务。

### Q33. 为什么不做微服务拆分？

答：因为这个项目目标是展示一条高并发下单链路，不是展示组织架构。过早拆微服务会引入注册中心、配置中心、网关、链路追踪和分布式事务，反而稀释重点。单体应用也可以清晰展示缓存、MQ、事务和索引。面试时我会说这是个人项目的有意收敛。生产级是否拆分要看团队规模、业务边界和部署需求。

### Q34. 为什么不做前端？

答：因为这个岗位是服务端研发，项目重点应该放在后端链路。前端页面对秒杀核心问题帮助不大，反而会占用时间。接口通过 curl 或压测工具就能验证主要能力。查询库存和订单的接口已经足够观察系统状态。面试展示时重点讲代码和链路，比展示页面更有价值。

### Q35. 你如何证明没有超卖？

答：可以从代码和压测结果两个角度证明。代码上 Redis Lua 保证入口扣减原子性，MySQL 条件更新保证最终库存不小于 0。压测上初始化库存 100，并发请求结束后检查订单数不能超过 100。再查库存事实表的可用库存，它不能为负。还要检查订单表没有同一活动、同一用户、同一 SKU 的重复记录。

### Q36. 你如何证明没有重复订单？

答：代码层有 Redis Set-N-X 入口防重，数据库层有 U-K User Sku 联合索引兜底。压测时可以让同一个用户连续请求 100 次，最后查询订单表应该只有 1 条。还可以按活动 ID、User ID、SKU ID 分组查重复，预期没有结果。即使 MQ 重复投递，消费者遇到唯一索引冲突也会 ACK。这个证明比只看接口返回更可靠。

### Q37. 这个项目的瓶颈在哪里？

答：第一瓶颈可能还是 Redis 热点库存，因为即使做了 bucket 分片，活动 SKU 仍然是高频访问对象。第二瓶颈是 MQ 消费速度，如果消费者写 MySQL 太慢，队列会积压。第三瓶颈是 MySQL 库存行更新，因为同一个 SKU 最终仍会竞争数据库库存行。个人项目里用 Redis 分片库存和 MQ 缓解入口压力。生产级可以继续做更细粒度库存分段、消费者扩容和数据库拆分。

### Q38. Redis 热 key 怎么处理？

答：热点 SKU 的库存 key 会承受大量访问，单 key 可能成为 Redis 压力点。项目里已经把 Redis 库存拆成多个 bucket，按用户 hash 选择分片扣减，分片扣不到时会扫描其他分片，尽量降低少卖。这样能把单 key 压力拆开，但也会带来分片库存不均、汇总对账和补偿复杂度。生产级还要结合 Redis Cluster、热点识别和活动预热一起做。

### Q39. 为什么 Redis Lua 返回 -1、0、1？

答：这三个返回值可以把库存不存在、库存不足和扣减成功区分开。库存不存在通常是活动没初始化或 Redis 数据丢失，应该返回库存未初始化。库存不足是正常业务失败，可以提示售罄。扣减成功才进入 MQ。清晰的返回码能让异常补偿更明确。

### Q40. 如何处理用户超时重试？

答：用户超时重试最容易导致重复请求。项目用 Set-N-X 的活动用户 SKU key 做幂等，第一次请求成功后，后续重试会被挡住。如果第一次请求已经进入 MQ，但订单还没创建，查询接口会返回排队中。这样不会因为 HTTP 超时生成多条订单。数据库联合唯一索引再做最终兜底。

### Q41. 如果用户抢到 Redis 库存但最终失败，体验怎么处理？

答：接口一开始只返回排队中，不承诺最终成功。最终结果要通过查询订单接口确认。如果 MQ 或 MySQL 阶段失败，查询可以返回失败。生产级还应该把失败原因标准化，并通过补偿任务或通知机制处理。这个项目主要展示后端一致性思路，没有做用户通知。

### Q42. 如何设计订单状态？

答：这个项目现在有未下单、排队中、成功、失败、已关闭和排队超时。排队中来自 Redis 幂等 key 或消息表还没消费完成。成功来自订单表已经有记录。失败可以来自库存不足、MQ 失败或 MySQL 兜底失败。排队超时由定时任务扫描长时间未完成的消息后写入 Redis 状态。生产级会继续扩展成待支付、已支付、取消、退款等完整订单状态机。

### Q43. 为什么 MQ 消费者要手动 ACK？

答：手动 ACK 可以让业务处理完成后再确认消息。自动 ACK 的问题是消息一到消费者就可能被确认，如果业务处理过程中服务宕机，消息就丢了。项目里只有订单事务成功、重复消费可接受或明确失败可记录时才 ACK。未知异常会 NACK 并进入死信队列。这样更符合可靠消费的基本要求。

### Q44. 死信队列在项目里怎么用？

答：项目配置了正常订单队列和死信队列。消费者遇到未知异常时 `basicNack(requeue=false)`，消息会被路由到死信队列。死信队列不是自动解决问题，而是给后续人工排查或补偿任务留入口。生产级会对死信数量设置告警，并提供重放工具。个人项目里保留结构，重点说明思路。

### Q45. 为什么初始化库存同时写 MySQL 和 Redis？

答：MySQL 是库存事实，Redis 是秒杀入口库存。初始化时两个地方都写，是为了让下单接口不必从 MySQL 读热点库存。Redis key 用于 Lua 扣减，MySQL 表用于消费者最终扣减和查询对账。如果 Redis 丢失，可以用 MySQL 的事实库存重新预热。这个设计体现的是缓存和数据库职责分离。

### Q46. 如果初始化库存重复调用会怎样？

答：项目里 MySQL 使用 `ON DUPLICATE KEY UPDATE`，所以同一个 SKU 可以重新初始化库存。Redis 也会直接覆盖库存 key。这个行为适合个人测试和压测前重置数据。生产级活动开始后一般不能随意重置库存，需要审批、日志和状态控制。否则可能破坏已经售出的订单和库存一致性。

### Q47. 为什么要统一返回 Result？

答：统一返回可以让接口响应格式稳定，调用方不用为每个接口适配不同结构。项目里成功时 `code=0`，失败时用不同 code 和 message 表示原因。对面试项目来说，这也体现了基本工程规范。真实生产还会有统一错误码体系和国际化文案。这里保持简单，够展示后端接口习惯。

### Q48. 为什么要全局异常处理？

答：全局异常处理可以避免 Controller 里到处写重复 try catch。参数错误、业务错误和未知异常可以统一转成 Result。这样接口不会把 Java 堆栈直接暴露给用户。项目里的 `GlobalExceptionHandler` 处理了参数校验、业务异常和兜底异常。生产级还会把异常打到日志系统和监控平台。

### Q49. 这个项目如何讲最终一致性？

答：我会说它不是强一致下单，而是入口快速抢资格，后端异步落库。Redis 扣库存和 MySQL 扣库存之间有短暂时间差，所以叫最终一致。MQ 负责把入口结果传到数据库消费端，MySQL 事务负责最终事实。异常时通过 Redis 回滚、死信队列、日志和对账补偿来恢复。核心是承认中间状态存在，并设计可恢复路径。

### Q50. 你明天面试最想强调哪三点？

答：第一是 Redis Lua 防超卖，因为它体现了我对并发原子性的理解。第二是 SETNX 加 MySQL 唯一索引防重复，因为它体现了入口优化和最终兜底的分层思路。第三是 RabbitMQ 异步削峰加 MySQL 事务，因为它体现了高并发下保护数据库和保证事实正确的能力。我也会主动说明这是个人项目简化版，不会夸大成生产系统。这样回答比较真实，也容易接受追问。

### Q51. 这个项目现在能不能做到每秒 10 万下单？

答：不能这么说，我不会把个人项目吹成单机每秒 10 万完整下单。更准确的说法是：现在项目补了 10 万用户同时涌入场景需要的关键结构，比如 token 资格池、Redis 库存分片、MQ 削峰、多实例部署示例和 Nginx 限流配置。10 万并发首先是入口能接住和快速失败，不是 10 万请求都写进 MySQL。真正写库速度要看消费者并发、数据库连接池、库存行锁和机器规格。面试里我会说这个项目展示的是架构方向和正确性，不虚构生产压测结果。

### Q52. 和以前版本相比，10 万并发方向主要改了什么？

答：以前所有用户都可以先拿 token，真正压力会更多落到 Redis 限流和下单链路。现在新增了库存倍数 token 资格池，默认只发库存几倍的短 TTL token，大量用户在 token 阶段就被快速拒绝。Redis 库存 bucket 也从更小的数量提升到 64，高并发 profile 可以配到 128。MQ 消费者并发和 prefetch 从硬编码改成配置，方便按 MySQL 能力调节。还补了多 Spring Boot 实例和 Nginx upstream 示例，所以方向从“单机链路正确”变成“可解释的多层削峰架构”。

### Q53. token 资格池会不会导致少卖？

答：有可能，所以它本质上是入口削流策略，不是最终库存事实。比如 token 过期、用户拿了 token 不下单，就可能造成短时间少卖。项目默认按库存的 3 倍发 token，就是为了在少卖和防刷之间做一个折中。生产级一般会动态补发 token，或者按实时转化率调整资格池，而不是固定倍数。面试里我会说，token 资格池的目标是保护系统，不是单独保证售罄，最终库存仍然由 Redis 库存和 MySQL 事实表控制。

### Q54. 别人用 Redis Cluster 抗 10 万秒杀，我们这个是不是一样？

答：现在项目已经补了 Redis Cluster 本地演示版，但我不会说它等同于生产级 Redis 集群。默认启动仍然是单 Redis，方便本地快速跑；Cluster 模式用 `docker-compose.redis-cluster.yml` 启 6 个节点，3 master 加 3 replica，应用用 `redis-cluster` profile 连接。关键点是，Cluster 解决多节点容量和高可用，但不能自动解决单个超级热 key。如果所有请求都打一个库存 key，在 Cluster 里它还是落到一个节点。项目保留 bucket 库存分片，就是为了让不同 bucket key 能分散到多个 Redis master 上。

### Q55. 如果真要做 10 万用户涌入，你的完整路径是什么？

答：第一层是网关和 Nginx 限流，先挡住明显异常流量。第二层是 token 资格池，只让库存倍数级别的用户拿到短 TTL token。第三层是 Redis Cluster 加库存 bucket，让抢资格过程在多 Redis master 上分摊。第四层是 RabbitMQ 排队削峰，数据库按消费者能力慢慢写。第五层是 MySQL 唯一索引、条件扣库存和对账补偿兜底。生产级还要补 MQ 集群、应用多实例、订单分库分表和监控告警，这样才是完整的 10 万用户涌入方案。

### Q56. 你怎么证明项目真的接了 Redis Cluster？

答：我会先说默认启动还是单 Redis，Redis Cluster 是单独 profile，避免本地开发复杂化。验证时执行 `docker compose -f docker-compose.yml -f docker-compose.redis-cluster.yml up -d --build`，会拉起 6 个 Redis 节点和一个 Cluster 版应用。然后用 `redis-cli cluster info` 和 `cluster nodes` 看 3 master 加 3 replica 是否正常。应用侧使用 `spring.data.redis.cluster.nodes`，Redisson 也会自动切到 Cluster 模式。最后调用初始化、拿 token、下单和查库存接口，验证 Lua 单 key 扣减、Set-N-X 和库存 bucket 在 Cluster 模式下都能跑通。

## 19. Java 并发 QA，至少 20 个

### Q1. synchronized 为什么不适合这个库存问题？

答：结论是 `synchronized` 只能解决单 JVM 内部互斥，不适合解决分布式库存。秒杀库存是多个请求、多个线程、甚至多个服务实例共同竞争的资源。一个实例里的锁不会影响另一个实例，所以不能保证全局库存安全。这个项目用 Redis Lua，是因为 Redis 是所有实例共享的入口状态。MySQL 条件更新再做最终兜底。

### Q2. synchronized 和 ReentrantLock 区别？

答：两者都能做单机互斥，但使用方式不同。`synchronized` 是 JVM 关键字，进入和退出代码块自动加解锁。`ReentrantLock` 是显式锁，可以尝试加锁、超时等待、公平锁和条件队列。业务代码简单时 `synchronized` 更直观，复杂并发控制时 `ReentrantLock` 更灵活。但在 Mini秒杀项目的全局库存场景里，它们都不是核心方案。

### Q3. volatile 能不能保证库存安全？

答：不能。`volatile` 只能保证可见性和一定的有序性，不能保证复合操作的原子性。库存扣减是“读取、判断、写回”的组合操作，多线程下仍然会丢失更新。比如两个线程都看到库存是 1，都可能继续扣减。这个项目需要的是 Redis Lua 或数据库条件更新这种原子判断加修改。

### Q4. CAS 是什么？

答：CAS 是 Compare And Swap，意思是比较当前值是否等于预期值，如果相等才更新。它是一种乐观并发控制，不需要直接阻塞线程。Java 的原子类底层常用 CAS 实现，比如 `AtomicInteger`。CAS 适合单机内存变量的并发更新，但不能直接解决多实例之间共享库存。秒杀库存更适合放在 Redis 或 MySQL 这种共享存储里。

### Q5. 线程池核心参数有哪些？

答：线程池核心参数包括核心线程数、最大线程数、空闲线程存活时间、任务队列、线程工厂和拒绝策略。核心线程数决定常驻处理能力，最大线程数决定突发扩展上限。队列决定任务堆积方式，拒绝策略决定系统过载时怎么失败。秒杀消费者也可以理解成一种受控并发，不能无限开线程写 MySQL。设置线程数要看数据库写入能力和 MQ 积压情况。

### Q6. 线程池队列满了怎么办？

答：队列满了说明系统处理能力跟不上请求进入速度。常见处理方式有拒绝、降级、限流、扩容或把任务转移到 MQ。不能简单把队列设得无限大，否则延迟会越来越高，内存也可能被打爆。Mini秒杀项目用 RabbitMQ 做削峰，本质上是把突发请求放到可观测的队列里。生产级还要根据队列积压和消费延迟做告警。

### Q7. ThreadLocal 是什么？

答：`ThreadLocal` 是线程本地变量，每个线程看到的是自己的副本。它常用于保存请求上下文、traceId、用户信息或数据库连接上下文。它不能用来做跨线程共享，也不适合存秒杀库存。使用线程池时要注意清理 ThreadLocal，否则线程复用会导致脏数据。这个项目如果接入链路追踪，可以用 ThreadLocal 传递 requestId。

### Q8. Java 里如何保证线程安全？

答：要先看共享资源在哪里。如果是单机内存，可以用不可变对象、锁、原子类、并发集合或线程封闭。如果是分布式共享资源，就要用 Redis、数据库、分布式锁或消息队列协调。Mini秒杀项目的库存不是 JVM 内存变量，所以不能只靠 Java 锁。它通过 Redis Lua 和 MySQL 条件更新保证全局正确性。

### Q9. 原子类适合什么场景？

答：原子类适合单 JVM 内高并发更新简单变量，比如计数器、序列号或状态标记。它的优势是开销比阻塞锁小，代码也比较清晰。项目里的本地订单号生成器用了原子计数做简化序列。但它不适合做全局库存，因为多个服务实例之间的原子类不共享。库存这类全局状态应该放在 Redis 或数据库。

### Q10. 单机锁和分布式锁区别？

答：单机锁只在一个 JVM 里生效，分布式锁要在多个进程或机器之间生效。单机锁可以用 `synchronized` 或 `ReentrantLock`，分布式锁常见实现是 Redis、Zookeeper 或数据库。这个项目用 Redisson 做了 Redis 分布式锁，但只保护库存初始化和预热这类低频管理动作。秒杀库存扣减不一定要用分布式锁，因为 Lua 原子扣减可以更直接。这个项目下单链路选择 Lua，是为了让库存判断和扣减更轻，避免锁等待、锁续期和锁释放带来的复杂度。

### Q11. 什么是可见性问题？

答：可见性问题是一个线程修改了共享变量，其他线程不一定马上看到。原因和 CPU 缓存、编译器优化、内存模型有关。`volatile`、锁和并发工具可以建立可见性保证。在秒杀项目里，库存状态不放在 JVM 共享变量里，所以不主要依赖 Java 内存模型。Redis 和 MySQL 是共享外部存储，所有实例通过它们看到统一状态。

### Q12. 什么是原子性问题？

答：原子性问题是一个操作看起来是一行代码，但底层可能分成多个步骤。比如 `stock--` 包含读、减、写，不是原子操作。多个线程同时执行会导致丢失更新。Mini秒杀项目用 Lua 把判断和扣减合成 Redis 内部的原子脚本。MySQL 也用一条条件更新 SQL 保证数据库层原子扣减。

### Q13. 什么是有序性问题？

答：有序性问题是程序代码顺序和实际执行顺序可能不完全一致。编译器和 CPU 会在不影响单线程结果的前提下重排序。多线程下如果缺少同步，就可能看到奇怪状态。Java 内存模型通过 volatile、锁和 happens-before 规则约束顺序。这个项目的核心状态变更交给 Redis 和 MySQL，不依赖本地指令顺序保证业务正确。

### Q14. AQS 是什么？

答：AQS 是 AbstractQueuedSynchronizer，是 Java 并发包里很多同步器的基础框架。`ReentrantLock`、`CountDownLatch`、`Semaphore` 等都和 AQS 有关。它核心是一个同步状态和一个等待队列。理解 AQS 有助于理解线程阻塞、唤醒和排队。面试里可以说这个项目不直接用 AQS，但 MQ 消费并发和连接池背后都会涉及这些基础能力。

### Q15. CountDownLatch 适合什么场景？

答：`CountDownLatch` 适合一个线程等待多个任务完成，比如并发压测时同时起跑或等待所有请求结束。它的计数只能递减，不能重复使用。测试 Mini秒杀项目时，可以用它让多个线程同时发送下单请求，更容易模拟并发竞争。但业务代码里不应该靠它控制库存。库存正确性仍然要靠 Redis Lua 和 MySQL。

### Q16. Semaphore 适合什么场景？

答：`Semaphore` 用来控制同时访问某个资源的线程数量。比如限制同时调用某个外部接口的并发，或者限制本地任务并发。它适合单进程内的并发阀门，不适合作为分布式秒杀库存。Mini秒杀项目的限流如果放在单实例内，可以用类似信号量的思想。但多实例场景还需要网关或 Redis 这样的共享限流。

### Q17. CompletableFuture 可以用在这个项目吗？

答：可以，但不是核心。`CompletableFuture` 适合在单个请求内并行调用多个独立任务，或者做异步编排。Mini秒杀项目的异步削峰使用 MQ 更合适，因为 MQ 能跨进程、可持久化、可积压、可重试。`CompletableFuture` 只是进程内异步，服务宕机任务就没了。订单这种关键业务更适合用消息队列。

### Q18. 为什么高并发服务怕阻塞？

答：阻塞会占住线程，而服务线程数是有限的。大量线程阻塞在数据库、网络或锁上，会导致请求排队、超时和线程池耗尽。秒杀场景尤其明显，因为瞬时请求很多。这个项目通过 Redis 快速判断、MQ 异步写库，减少请求线程长时间阻塞。消费者侧也要控制并发，避免全部阻塞在 MySQL。

### Q19. 如何设置消费者并发？

答：消费者并发不是越高越好，要看 MySQL 能承受多少写入和锁竞争。并发太低，MQ 积压严重；并发太高，数据库连接池、行锁和 IO 压力会上升。项目里配置了并发消费者和 prefetch，体现可控消费。生产级应该根据消费延迟、队列长度、数据库 CPU 和锁等待动态调整。最终目标是系统整体稳定，而不是单点跑满。

### Q20. Java 并发在这个项目里的核心认识是什么？

答：我的核心认识是先判断共享资源边界。库存不是单机共享变量，而是全局业务资源，所以不能用单机锁解决。Java 并发知识能帮助我理解线程池、阻塞、可见性和原子性，但项目正确性要落到 Redis、MQ 和 MySQL。入口用 Redis Lua 做原子扣减，消费端用事务和唯一索引兜底。这样回答能把八股知识和项目连接起来。

## 20. MySQL QA，至少 20 个

### Q1. 为什么要唯一索引？

答：唯一索引用来保证数据层面的业务唯一性。这个项目里最重要的是活动 ID、User ID 和 SKU ID 的联合唯一索引，它保证一个用户对一个活动 SKU 只能有一条订单。即使 Redis Set-N-X 失效、HTTP 重试或 MQ 重复消费，数据库也不会生成重复订单。应用层判断可能因为并发失效，但唯一索引是 MySQL 的最终约束。它是幂等设计的最后防线。

### Q2. 为什么 User ID 加 SKU ID 做唯一索引？

答：秒杀业务通常要求同一个用户对同一个活动商品只能买一次。单独对 User ID 建唯一索引会导致用户只能买一个商品，太严格。单独对 SKU ID 建唯一索引会导致一个商品只能被一个用户购买，也不对。User ID 和 SKU ID 的组合键正好表达“一人一商品一单”的业务规则。当前项目还加了 activityId，避免不同活动里的同一个 SKU 互相冲突。这个规则放在数据库里比只写在代码里更可靠。

### Q3. 事务在项目里怎么用？

答：消费者创建订单时开启 MySQL 事务。事务里先插入订单，再扣减库存，最后写日志。只要其中任何关键步骤失败，就回滚整个事务。这样不会出现订单插入成功但库存没扣，或者库存扣了但订单没有的情况。事务保证的是 MySQL 内部状态一致。

### Q4. MySQL 行锁什么时候产生？

答：InnoDB 在更新命中索引记录时会对相关记录加行锁。这个项目的库存扣减 SQL 根据活动 ID 和 SKU ID 更新库存事实表，因为这两个字段有联合唯一索引，所以会锁住对应库存行。行锁能保证同一行库存不会被并发更新乱掉。但大量请求竞争同一活动 SKU 时，行锁也会成为瓶颈。所以前面要用 Redis 和 MQ 削峰。

### Q5. 可用库存大于 0 有什么作用？

答：它是数据库层防超卖的条件。只有可用库存大于 0 时，更新才会成功。并发情况下，InnoDB 会串行化同一行更新，后来的事务会重新判断条件。如果库存已经是 0，影响行数就是 0，业务应该回滚。它保证 MySQL 不会扣出负库存。

### Q6. 乐观锁和悲观锁区别？

答：悲观锁认为冲突经常发生，所以先加锁再操作。乐观锁认为冲突不一定发生，更新时通过版本号或条件判断是否成功。这个项目的“可用库存大于 0”更像条件更新兜底，也可以扩展为 version 乐观锁。悲观锁正确但可能阻塞严重，乐观锁吞吐更好但失败后要重试或返回。秒杀热点库存一般要避免大量请求直接竞争数据库锁。

### Q7. 索引为什么能加速查询？

答：索引本质上是额外的数据结构，帮助数据库快速定位记录。没有索引时，数据库可能要全表扫描。B+ 树索引可以把查找复杂度降到对数级，并且适合范围查询。项目里按活动 ID 加 SKU ID 查库存，按活动 ID 加 User ID 加 SKU ID 查订单都需要索引。索引提升查询速度，但会增加写入维护成本。

### Q8. 索引失效有哪些情况？

答：常见情况包括对索引列使用函数、隐式类型转换、最左前缀不满足、前导模糊查询和低选择性条件不合适。比如组合索引是活动 ID、User ID、SKU ID，如果查询时跳过前面的活动 ID 或 User ID，就不能充分利用最左前缀。项目里查询订单时同时带 activityId、userId 和 skuId，能很好利用唯一索引。写 SQL 时要让条件和索引设计匹配。否则建了索引也可能走全表扫描。

### Q9. B+ 树为什么适合数据库索引？

答：B+ 树扇出高，树高低，磁盘 IO 次数少。它的非叶子节点只存 key，叶子节点存数据或主键，并且叶子节点有链表，适合范围查询。数据库查询通常受磁盘和页读取影响，所以减少 IO 很重要。相比二叉树，B+ 树更适合块设备和页缓存。MySQL InnoDB 的主键索引和二级索引都基于 B+ 树思想。

### Q10. MySQL 和 Redis 的职责区别？

答：Redis 负责高并发、低延迟的入口判断，MySQL 负责持久化和最终事实。Redis 的数据可以重建，MySQL 的订单和库存不能随便丢。这个项目里 Redis 库存先扣，是为了抗流量；MySQL 库存后扣，是为了保证真实结果。两者不是互相替代，而是分层协作。面试时要强调 MySQL 才是最终事实。

### Q11. 什么是聚簇索引？

答：InnoDB 的聚簇索引是数据和主键索引放在一起的结构。表数据按照主键 B+ 树组织，叶子节点就是完整行数据。一个表只能有一个聚簇索引。项目里的 `id BIGINT PRIMARY KEY AUTO_INCREMENT` 就是聚簇索引。二级索引叶子节点通常存主键值，再回表查完整数据。

### Q12. 什么是回表？

答：回表是通过二级索引找到主键后，再到聚簇索引查完整行。比如只通过 `idx_sku_id` 找订单，但查询字段不在索引里，就可能回表。回表会增加一次索引查找成本。可以通过覆盖索引减少回表。项目查询订单按唯一索引命中少量数据，回表成本可接受。

### Q13. 什么是覆盖索引？

答：覆盖索引是查询需要的字段都能从索引里拿到，不需要回表。它可以减少 IO，提高查询性能。比如一个查询只需要 `user_id`、`sku_id`、`order_id`，可以设计包含这些字段的索引。但索引越多写入成本越高。秒杀订单写入频繁，所以不能为了所有查询无限加索引。

### Q14. MySQL 隔离级别有哪些？

答：常见隔离级别有读未提交、读已提交、可重复读和串行化。MySQL InnoDB 默认通常是可重复读。隔离级别越高，并发性能可能越低，但一致性更强。这个项目主要依赖单条条件更新和唯一索引，不强依赖复杂隔离级别。库存扣减由行锁和条件判断保证正确。

### Q15. 什么是幻读？

答：幻读是同一个事务里按条件查询，另一个事务插入了满足条件的新行，导致前后看到的行集合不同。InnoDB 在可重复读下通过 MVCC 和 next-key lock 处理很多幻读问题。这个项目主要是按唯一 SKU 更新一行库存，不是范围插入场景。订单唯一性也由唯一索引保证。面试时可以简单说明，不强行把幻读套到项目里。

### Q16. 什么是 MVCC？

答：MVCC 是多版本并发控制，让读写可以在一定程度上并发执行。InnoDB 通过 undo log 和 read view 实现一致性读。读请求可以看到某个版本的数据，不一定阻塞写。这个项目的库存扣减是当前读，会加锁并修改数据，不是普通快照读。理解 MVCC 有助于解释为什么查询和更新的行为不同。

### Q17. 慢 SQL 怎么排查？

答：先看慢查询日志，确认 SQL、耗时、扫描行数和返回行数。再用 `EXPLAIN` 看是否走索引、访问类型和额外操作。然后结合表结构、索引、数据量和业务条件优化。项目里高频 SQL 是按 SKU 扣库存和按用户 SKU 查订单，索引必须匹配。生产级还要监控连接池、锁等待和磁盘 IO。

### Q18. 为什么订单表要有 `order_id` 唯一索引？

答：`order_id` 是对外订单号，需要保证全局唯一。即使数据库主键 `id` 已经唯一，对外暴露时也通常不用自增主键。唯一索引可以防止订单号生成器异常导致重复订单号。项目里的订单号生成器是个人项目简化版，生产级要换成更可靠的全局 ID。唯一索引是最后的保护。

### Q19. 为什么库存表有 `sold_count`？

答：已售数量可以快速看到售卖进度，也方便对账。理论上已售数量可以从订单表统计，但高频查询时每次聚合订单会比较重。库存扣减时同步增加已售数量，能保持库存视图清晰。它和可用库存必须在同一个事务或同一条 SQL 中更新。项目里扣库存 SQL 同时减可用库存、加已售数量。

### Q20. MySQL 在这个项目里的核心认识是什么？

答：MySQL 不应该承接所有秒杀入口流量，但必须负责最终正确性。Redis 和 MQ 可以提高吞吐和削峰，但不能替代事务、唯一索引和条件更新。项目里 MySQL 的重点是订单唯一性、库存非负和事务一致。面试时我会强调数据库是最后事实，而不是把缓存扣减当作最终成功。这个认识比单纯会写 SQL 更重要。

## 21. Redis QA，至少 20 个

### Q1. Redis 为什么快？

答：Redis 快主要因为它基于内存操作，避免了大部分磁盘随机 IO。它的数据结构实现也很高效，比如字符串、哈希、跳表和压缩列表等。Redis 命令执行模型简单，单线程避免了复杂锁竞争。网络层使用 IO 多路复用，可以处理大量连接。Mini秒杀项目用 Redis 承接热点库存，就是利用它低延迟的特点。

### Q2. Redis 单线程为什么还能高性能？

答：Redis 的命令执行是单线程为主，但网络 IO 使用多路复用，可以高效处理很多连接。大部分 Redis 命令是内存操作，执行时间很短，所以单线程也能跑得很快。单线程还避免了多线程锁竞争和上下文切换。真正要避免的是慢命令和大 key 操作。这个项目的 Lua 脚本很短，只做 GET、判断和 DECR，适合 Redis 执行。

### Q3. Redis Lua 为什么能保证原子性？

答：Redis 执行 Lua 脚本时，会把脚本作为一个整体执行。脚本执行期间不会穿插其他客户端命令，所以判断库存和扣库存之间没有并发窗口。这个原子性来自 Redis 的执行模型，而不是 Java 代码。项目里 Lua 先 GET 库存，再判断，再 DECR，这三个动作对外表现为一个原子操作。它正好解决 GET 再 DECR 的竞态问题。

### Q4. GET 再 DECR 为什么不安全？

答：因为 GET 和 DECR 是两个独立命令，中间可能插入其他请求。多个请求同时 GET 到库存大于 0，然后都执行 DECR，就可能扣成负数。应用层加判断无法消除这个窗口。Lua 把判断和扣减放到 Redis 内部一次执行，才是安全的。这个是秒杀防超卖里非常典型的点。

### Q5. SETNX 为什么能做幂等？

答：Set-N-X 的语义是 key 不存在才设置成功。用活动 ID、User ID 和 SKU ID 拼成 key 后，第一次请求成功，后续重复请求会设置失败。这样能挡住用户重复点击和网络重试。项目里 Set-N-X 只是入口幂等，最终还要靠 MySQL 联合唯一索引。双层幂等比单层更稳。

### Q6. Redis 幂等 key 过期时间怎么设置？

答：过期时间要覆盖正常排队和消费时间，不能太短。太短会导致订单还没落库，用户又能重复进入链路。太长会导致失败请求恢复慢，用户长时间不能重试。项目默认设置 30 分钟，适合个人演示。生产级应该根据活动时长、MQ 延迟和订单超时时间来设定。

### Q7. Redis 库存和 MySQL 不一致怎么办？

答：先判断不一致发生在哪个阶段。如果 MQ 发送失败，当前项目会依靠本地消息表保留待补发记录，而不是直接吞掉请求。如果消费失败，需要通过死信队列、消息重投和补偿任务处理。项目里的对账和恢复不会简单用 Redis 数值做最终结果，而是以 MySQL 为事实源。Redis 宕机或 key 丢失时，会按 MySQL 可用库存减未完成消息数重建入口库存。关键点是 MySQL 是最终事实，Redis 是可恢复的入口状态。

### Q8. 缓存击穿、穿透、雪崩是什么？

答：缓存穿透是查询不存在的数据，缓存和数据库都被打。缓存击穿是热点 key 过期，大量请求同时打到数据库。缓存雪崩是大量 key 同时失效或 Redis 故障，导致数据库压力暴增。Mini秒杀项目的库存 key 是热点 key，如果活动中丢失就接近击穿问题。生产级要预热库存、限制回源和保护数据库。

### Q9. 分布式锁和 Lua 扣库存有什么区别？

答：分布式锁是先拿锁，再执行一段业务逻辑，最后释放锁。Lua 扣库存是把判断和扣减直接放到 Redis 里原子执行。对于单个库存 key 的扣减，Lua 更轻量，少了一次加锁和释放锁的流程。分布式锁适合保护更复杂的跨资源临界区，比如库存初始化、库存预热、活动状态切换或补偿任务。这个项目已经用 Redisson 实现了 SKU 级分布式锁，但只放在库存初始化/预热上。热点下单链路仍然用 Lua 扣 Redis 库存，因为加锁再扣库存会增加网络往返、锁等待和锁续期复杂度。面试时可以说：我知道分布式锁怎么做，但不会为了堆技术把它放到不适合的位置。

### Q10. Redis 挂了如何降级？

答：Redis 挂了不能让所有请求直接打 MySQL，否则数据库可能被压垮。项目里的策略是进入恢复态，获取 token 和下单接口都返回 503，不继续放流量。等 Redis 重启后，再用恢复接口按 MySQL 可用库存减未完成消息数重建库存。恢复成功后入口才重新打开。生产级应该用 Redis 高可用部署减少故障概率，并把恢复流程接入告警、审批和自动化编排。

### Q11. Redis key 怎么命名？

答：key 命名要表达业务含义和维度。项目里库存 key 是 `seckill:stock:{activityId}:{skuId}`，用户幂等 key 是 `seckill:user:{activityId}:{userId}:sku:{skuId}`。这种命名方便排查，也方便按前缀统计。活动 ID 必须进入 key，否则不同活动里的同一个 SKU 会冲突。key 设计要兼顾可读性和唯一性。

### Q12. Redis key 需要加活动 ID 吗？

答：要加活动 ID。这个项目已经把库存 key 扩成 `seckill:stock:{activityId}:{skuId}`，订单唯一索引也带 activityId。如果同一个 SKU 参加多个活动，只用 SKU 会冲突。活动 ID 是秒杀业务很自然的隔离维度。面试时可以说这是从“小项目”往真实业务靠拢的一步。

### Q13. Redis 库存 key 要不要设置过期时间？

答：活动库存 key 可以设置过期时间，但要谨慎。过期时间应该晚于活动结束和订单消费完成时间。太早过期会导致库存不存在，影响下单。个人项目没有强制设置库存 TTL，方便压测和观察。生产级会结合活动生命周期做预热和清理。

### Q14. 什么是热 key？

答：热 key 是访问频率特别高的 key。秒杀库存就是典型热 key，因为所有用户都在抢同一个 SKU。热 key 会让 Redis 单节点 CPU 或网络成为瓶颈。处理方式包括限流、库存分片、本地只读缓存和活动预热。这个项目已经做了简化版 bucket 分片，但生产级还要结合 Redis Cluster、热点监控和更完整的分片归并方案。

### Q15. 什么是大 key？

答：大 key 是 value 很大或者集合元素很多的 key。大 key 会导致命令执行慢、网络传输慢和阻塞风险。秒杀库存 key 是简单字符串，不是大 key。幂等 key 也是单个字符串，压力来自数量而不是 value 大小。生产级要监控大 key，避免阻塞 Redis。

### Q16. Redis 持久化方式有哪些？

答：Redis 常见持久化有 RDB 和 AOF。RDB 是周期性快照，恢复快但可能丢最近数据。AOF 记录写命令，数据更完整但文件更大。秒杀入口库存即使丢失，也应该能从 MySQL 重新预热。订单事实不能只依赖 Redis 持久化，必须落 MySQL。

### Q17. Redis 主从复制有什么风险？

答：Redis 主从复制通常是异步的，主节点写入后从节点可能还没同步。如果主节点这时故障切换，可能丢失少量写入。秒杀库存扣减对一致性敏感，所以生产级要评估 Redis 高可用带来的数据窗口。MySQL 最终兜底可以减少脏数据成为事实。必要时要做对账和补偿。

### Q18. Redis Cluster 能解决什么问题？

答：Redis Cluster 可以把 key 分散到多个节点，提升容量和吞吐，也提供一定高可用能力。它适合多 key、多业务场景。单个超级热 key 仍然可能集中在一个分片上，所以 Cluster 不是热 key 的万能解法。这个项目现在提供了 6 节点 Redis Cluster 本地演示，并保留库存 bucket 分片，让不同 bucket key 有机会分散到不同 master。生产级还要继续做热点监控、故障切换演练和跨机压测。

### Q19. Lua 脚本会有什么风险？

答：Lua 脚本不能写得太慢，否则会阻塞 Redis 执行其他命令。脚本里不要做大循环或处理大 key。还要注意脚本结果和业务返回码清晰。项目里的脚本非常短，只做库存判断和 DECR，风险较低。生产级要监控慢脚本和 Redis 延迟。

### Q20. Redis 在这个项目里的核心认识是什么？

答：Redis 是高并发入口工具，不是最终交易数据库。它适合快速做库存资格判断、用户幂等和服务端限流，但最终订单必须落 MySQL。Lua 解决的是入口原子扣减和计数限流，Set-N-X 解决的是入口重复请求。Redis 异常时要降级和重建，不能让数据库裸奔。这个认识能避免把缓存当数据库用。

## 22. MQ QA，至少 15 个

### Q1. MQ 为什么能削峰？

答：MQ 把瞬时请求变成队列里的待处理消息。接口侧只要完成抢资格、写本地消息表和投递，就可以快速返回，不需要同步等数据库写入。消费者按固定并发慢慢处理，数据库看到的是平滑流量。削峰不是让请求消失，而是把压力从瞬时变成可排队。Mini秒杀项目正是用 RabbitMQ 保护 MySQL。

### Q2. MQ 消息丢失怎么办？

答：消息丢失要分生产端、Broker 和消费端。生产端可以用 publisher confirm 和本地消息表确认消息真的发出。Broker 侧要用持久化交换机、队列和消息。消费端要手动 ACK，业务成功后再确认。项目已经有本地消息表、confirm/return、手动 ACK、持久化队列和失败重投骨架，生产级还要补告警、人工重放和更完整的消息状态机。

### Q3. MQ 重复消费怎么办？

答：重复消费不能避免，只能让业务幂等。项目用活动 ID、User ID、SKU ID 的联合唯一索引兜底。消费者重复插入时会触发 DuplicateKeyException，然后 ACK 消息，不再重复创建订单。本地消息表会同步把消息标记为已消费。生产级还可以增加消费记录表，以 messageId 或 requestId 做更细的消费幂等。核心是不能假设消息只消费一次。

### Q4. MQ 消息堆积怎么办？

答：先看堆积原因，是消费者太慢、数据库慢、异常重试多，还是流量超过设计。短期可以扩消费者或降低入口流量。长期要优化消费者 SQL、数据库容量和队列分区。不能盲目无限扩消费者，因为可能把 MySQL 打垮。Mini秒杀项目的消费者并发应该跟数据库写能力匹配。

### Q5. 死信队列是什么？

答：死信队列是存放无法正常消费消息的队列。消息被拒绝且不重回队列、过期或队列超长时，都可能进入死信队列。死信队列方便后续排查、告警和人工重放。它不是自动补偿机制，而是异常消息的隔离区。项目里未知消费异常会 NACK 到死信队列。

### Q6. 消费者 ACK 失败怎么办？

答：如果业务成功但 ACK 失败，Broker 可能认为消息没确认，之后重新投递。这个时候消费者必须支持幂等。Mini秒杀项目依靠订单联合唯一索引处理重复消息。重复投递时插入订单失败，但这说明订单已经存在，直接 ACK 即可。可靠消费的核心就是业务成功和 ACK 之间的窗口要靠幂等兜底。

### Q7. 如何保证最终一致性？

答：最终一致性靠消息传递、幂等消费、失败重试和补偿对账。Redis 扣库存后，本地消息表先记录请求，MQ 再把请求传给消费者，消费者把结果落到 MySQL。消费成功后 MySQL 成为最终事实。如果中间失败，就通过消息重投、死信队列、日志和对账任务修复。项目展示了基本结构，生产级要补完整 confirm、告警和人工补偿入口。

### Q8. 为什么不用同步写数据库？

答：同步写数据库会让所有入口请求都占用数据库连接和行锁。秒杀高峰下，数据库很容易成为瓶颈，接口延迟也会被拉高。异步 MQ 可以让接口快速返回，把写库压力变成可控消费。代价是用户要查询最终状态。这个权衡适合秒杀这种高峰明显的业务。

### Q9. MQ 和线程池削峰有什么区别？

答：线程池是进程内队列，服务重启后任务可能丢失，也不方便跨实例协调。MQ 是独立中间件，可以持久化、跨进程、可积压、可监控。订单创建这种关键任务更适合 MQ。线程池可以做本地异步，但不适合承担核心交易消息。Mini秒杀项目用 MQ 是为了可靠削峰和解耦。

### Q10. 消费者数量怎么设置？

答：消费者数量要根据数据库写入能力设置。太少会导致队列积压，太多会导致数据库锁等待和连接池压力。可以先用压测找出单消费者吞吐，再逐步增加并发观察 MySQL 指标。还要设置 prefetch，避免单个消费者一次拿太多消息。目标是稳定消费，而不是把队列瞬间清空。

### Q11. RabbitMQ exchange 和 queue 是什么关系？

答：生产者把消息发到 exchange，exchange 根据 routing key 和 binding 把消息路由到 queue。消费者从 queue 里取消息。这个项目使用 direct exchange，因为订单消息只需要按明确 routing key 投递到一个队列。结构简单，适合面试项目展示。生产级可以按业务拆多个 exchange 和 queue。

### Q12. 什么是消息持久化？

答：消息持久化是让队列、交换机和消息在 Broker 重启后尽量不丢。队列和交换机要声明为 durable，消息也要持久化。Spring AMQP 默认对普通消息通常会设置持久化，但生产级需要明确检查。即使持久化，也要配合 confirm 才能知道消息是否真的到达 Broker。可靠消息是多个环节共同保证的。

### Q13. 什么是 publisher confirm？

答：publisher confirm 是 RabbitMQ 告诉生产者消息是否到达 Broker 的机制。没有 confirm，生产者调用发送成功不代表 Broker 真的收到。项目里先写本地消息表，发送时带 CorrelationData，收到 confirm ack 后标记为已发送，confirm nack 或 return callback 会标记为可重试状态。失败或超时由后台任务重发。生产级还要在这个基础上加告警、人工重放和更细的消息状态机。

### Q14. 什么是 requeue？

答：requeue 是消费失败后是否把消息重新放回队列。如果一直 requeue，毒消息可能被反复消费，拖垮系统。项目里未知异常使用 `basicNack(requeue=false)`，让消息进入死信队列。对于临时故障，可以设计有限次数重试，再进死信。不能无脑无限重试。

### Q15. MQ 在这个项目里的核心认识是什么？

答：MQ 不是为了让业务变复杂，而是为了让高峰流量可控。它把入口请求和数据库写入解耦，让 MySQL 按能力消费。引入 MQ 后必须处理丢失、重复、顺序、积压和死信。Mini秒杀项目用本地消息表处理发送失败，用唯一索引处理重复，用手动 ACK 和死信队列处理消费异常。面试时要讲清楚收益和代价。

## 23. 操作系统 QA，至少 15 个

### Q1. 进程和线程区别？

答：进程是资源分配的基本单位，线程是 CPU 调度的基本单位。一个进程可以有多个线程，线程共享进程的内存和文件句柄等资源。线程切换通常比进程切换轻，但线程之间共享内存也更容易出现并发问题。Spring Boot 服务运行在一个 Java 进程里，请求处理和 MQ 消费由多个线程完成。理解进程和线程有助于理解高并发服务的资源消耗。

### Q2. 上下文切换是什么？

答：上下文切换是 CPU 从一个线程或进程切到另一个线程或进程时保存和恢复现场的过程。它会消耗 CPU 时间，但不直接产生业务价值。高并发服务如果创建过多线程，反而可能因为上下文切换变慢。Mini秒杀项目通过 MQ 控制消费者并发，就是避免写库线程无限增长。线程数要匹配 CPU 和 IO 能力。

### Q3. 用户态和内核态区别？

答：用户态是普通应用程序运行的状态，内核态是操作系统内核运行的状态。网络 IO、文件 IO、线程调度等通常需要进入内核态。用户态和内核态切换有成本，所以高性能服务会尽量减少不必要的系统调用。Java 服务处理 HTTP、Redis、MySQL 和 MQ 都会涉及网络 IO。理解这个点能解释为什么连接池和 IO 多路复用重要。

### Q4. IO 阻塞是什么？

答：IO 阻塞是线程等待磁盘、网络或其他外部资源返回结果。阻塞期间线程不能继续处理其他任务，但仍然占用线程资源。高并发服务中大量线程阻塞，会导致线程池耗尽和请求排队。Mini秒杀项目用 Redis 快速处理入口，用 MQ 异步写库，减少请求线程阻塞在 MySQL 上。消费者阻塞也要通过并发数和连接池控制。

### Q5. Page Cache 是什么？

答：Page Cache 是操作系统用内存缓存磁盘文件内容的机制。读文件时如果命中 Page Cache，就不需要直接访问磁盘。写文件时也可能先写到缓存，再由系统异步刷盘。MySQL、RabbitMQ 和日志系统都会受到 Page Cache 影响。理解 Page Cache 有助于理解为什么写入不一定马上落到物理磁盘。

### Q6. 文件写入为什么可能先写到缓存？

答：因为操作系统为了提高性能，会把写入先放到内存缓存中，再异步刷到磁盘。这样应用看到写入返回，不一定代表物理磁盘已经完成写入。数据库和 MQ 要通过 fsync、事务日志和持久化策略提高可靠性。RabbitMQ 持久化消息也不是一句配置就绝对不丢，还要看确认机制和刷盘策略。面试时可以用这个解释可靠消息为什么要多层保证。

### Q7. 连接池为什么能提升性能？

答：连接池复用已经建立的连接，避免频繁创建和销毁连接。数据库连接和网络连接建立成本比较高，还涉及认证和资源分配。连接池还能限制最大并发，保护下游服务。Mini秒杀项目访问 MySQL、Redis 和 RabbitMQ 都依赖连接管理。连接池太小会排队，太大可能压垮下游。

### Q8. CPU 密集型和 IO 密集型区别？

答：CPU 密集型主要消耗计算资源，比如加密、压缩和复杂计算。IO 密集型主要等待网络、磁盘或数据库返回。Java 后端大多数接口是 IO 密集型，因为要访问 Redis、MySQL 和 MQ。IO 密集型可以适当设置更多线程，但不能无限增加。Mini秒杀项目的消费者并发要根据 MySQL IO 和锁等待调整。

### Q9. 高并发服务为什么怕阻塞？

答：阻塞会占住工作线程，线程池容量有限。大量请求同时阻塞时，新请求只能排队或被拒绝。阻塞还会放大超时重试，造成更多重复请求。Mini秒杀项目用 Redis 快速判断和 MQ 异步化，就是减少入口请求阻塞时间。对服务端来说，稳定地快速失败也比无限阻塞好。

### Q10. 系统负载高怎么排查？

答：先看 CPU、内存、磁盘 IO、网络和进程线程数。然后结合应用指标，看接口延迟、错误率、数据库连接池、Redis 延迟和 MQ 积压。CPU 高可能是计算、频繁 GC 或上下文切换；IO 高可能是数据库或日志写入慢。Mini秒杀项目压测时如果负载高，要看是 Redis 热 key、MySQL 行锁还是消费者过多。排查要从系统指标到业务指标逐层缩小。

### Q11. 什么是 epoll？

答：epoll 是 Linux 下高效的 IO 多路复用机制。它可以让一个线程管理大量 socket 连接，而不是每个连接一个线程阻塞等待。Redis、Netty 等高性能网络组件都和 IO 多路复用思想有关。Spring Boot 默认 Web 容器也会使用线程池处理请求。理解 epoll 有助于解释 Redis 单线程为什么能处理大量连接。

### Q12. 什么是零拷贝？

答：零拷贝是减少数据在内核态和用户态之间复制的技术。它可以降低 CPU 消耗，提高文件或网络传输效率。Kafka 等中间件常用零拷贝提升吞吐。RabbitMQ 的定位和实现不同，但消息中间件都关心网络和磁盘效率。这个项目不直接实现零拷贝，但理解它有助于回答中间件性能问题。

### Q13. 什么是内存泄漏？

答：内存泄漏是对象已经不再需要，但仍然被引用，导致 GC 无法回收。Java 中常见原因包括静态集合、ThreadLocal 未清理、监听器未注销和缓存无界增长。秒杀系统如果把请求状态无限放内存，也可能造成泄漏。Mini秒杀项目把幂等状态放 Redis 并设置 TTL，是为了避免本地内存无限增长。生产级还要监控 JVM 堆和 GC。

### Q14. 什么是 GC 停顿？

答：GC 停顿是 JVM 垃圾回收时应用线程暂停或受影响的时间。停顿过长会导致接口延迟上升，甚至触发超时重试。高并发服务要关注对象创建速度、堆大小和 GC 日志。Mini秒杀项目的入口链路应该尽量轻量，避免每个请求创建大量临时对象。生产级需要监控 P99 延迟和 GC 指标。

### Q15. OS 基础在项目里怎么体现？

答：它体现在高并发服务的资源意识上。线程、连接、IO、上下文切换、缓存和磁盘刷写都会影响系统稳定性。Mini秒杀项目用 Redis 和 MQ，不只是技术选型，也是在减少请求线程阻塞和数据库 IO 峰值。面试时不需要把操作系统讲得很学术，而是要能把它和服务端性能联系起来。这样回答更贴近工程岗位。

## 24. 计算机网络 QA，至少 15 个

### Q1. TCP 三次握手是什么？

答：三次握手是 TCP 建立连接的过程。客户端发 SYN，服务端回 SYN+ACK，客户端再回 ACK。这样双方确认彼此的发送和接收能力都正常。HTTP、MySQL、Redis 和 RabbitMQ 底层都依赖 TCP 连接。连接池能复用连接，避免每次请求都重新握手。

### Q2. TCP 四次挥手是什么？

答：四次挥手是 TCP 关闭连接的过程。因为 TCP 是全双工，客户端和服务端两个方向都要分别关闭。主动关闭方会进入 TIME_WAIT 状态，等待可能迟到的包消失。大量短连接会产生很多 TIME_WAIT，影响端口和资源。后端服务通常使用长连接和连接池减少这个成本。

### Q3. HTTP 和 TCP 区别？

答：TCP 是传输层协议，负责可靠字节流传输。HTTP 是应用层协议，定义请求和响应语义。HTTP 通常运行在 TCP 之上，也可以在新版本里运行在 QUIC 等协议上。Mini秒杀项目的接口是 HTTP，但访问 Redis、MySQL、RabbitMQ 也都离不开 TCP 连接。面试时要分清协议层次。

### Q4. HTTP 状态码怎么理解？

答：HTTP 状态码表示协议层请求结果，比如 200 成功、400 参数错误、500 服务端错误。业务系统通常还会在响应体里定义业务 code。Mini秒杀项目用统一 Result，`code=0` 表示业务成功，重复下单或库存不足用业务 code 表示。实际项目里 HTTP 状态码和业务状态码要配合使用。不要把所有错误都模糊成成功。

### Q5. 长连接和短连接区别？

答：短连接每次请求都建立和关闭连接，开销大。长连接复用 TCP 连接，可以减少握手和挥手成本。数据库连接池、Redis 连接池和 MQ 连接都是长连接思想。高并发服务如果每次都新建连接，会浪费大量资源。Mini秒杀项目本地启动依赖这些客户端连接池。

### Q6. 超时重试为什么会导致重复请求？

答：客户端超时不代表服务端没有处理成功。可能服务端已经完成 Redis 扣库存或已经发送 MQ，只是响应在网络上超时了。客户端如果重试，就会产生重复请求。Mini秒杀项目用 SETNX 和唯一索引处理这个问题。接口幂等是高并发服务必须考虑的基本能力。

### Q7. 为什么接口要做幂等？

答：因为网络是不可靠的，重试、重复点击、代理重放和 MQ 重复消费都可能发生。没有幂等，重复请求可能创建多条订单或重复扣库存。Mini秒杀项目在入口用 SETNX，在数据库用唯一索引。这样即使请求重复，最终事实也不会重复。幂等是可靠服务端设计的基础。

### Q8. 网关限流怎么做？

答：网关可以按 IP、用户、设备、SKU、活动维度做限流。算法可以用令牌桶、漏桶、固定窗口或滑动窗口。网关限流的好处是足够前置，能在请求进入业务服务前保护系统。秒杀场景还可以加验证码或排队页。Mini秒杀项目当前没有网关，但生产级会把限流放在业务服务之前。

### Q9. TCP 如何保证可靠传输？

答：TCP 通过序列号、确认应答、超时重传、滑动窗口和拥塞控制保证可靠传输。它能保证字节流按序到达，但不能保证业务请求只执行一次。比如响应丢了，客户端重试，服务端可能执行两次。业务幂等仍然要应用层自己做。Mini秒杀项目的 SETNX 和唯一索引就是应用层可靠性。

### Q10. 服务端连接数过多怎么办？

答：先看连接来源，是客户端长连接过多、下游连接泄漏，还是 TIME_WAIT 堆积。可以通过连接池限制、网关限流、keepalive 调整和超时设置处理。对数据库连接尤其要谨慎，连接数太多会压垮 MySQL。Mini秒杀项目用 MQ 削峰，也是为了避免大量请求同时占用数据库连接。连接数是高并发服务的关键资源。

### Q11. HTTP keep-alive 有什么作用？

答：keep-alive 让多个 HTTP 请求复用同一个 TCP 连接。它可以减少握手成本，提高吞吐和降低延迟。高并发下，复用连接比频繁建连更稳定。但连接也不能无限保持，要设置合理超时。服务端和客户端连接池都要配合。

### Q12. 什么是反向代理？

答：反向代理位于客户端和后端服务之间，代表后端接收请求。Nginx、网关和负载均衡都可以扮演反向代理角色。它可以做路由、限流、TLS 终止、压缩和负载均衡。生产级 Mini秒杀项目会把限流和鉴权放到反向代理或网关层。这样业务服务压力更可控。

### Q13. 什么是负载均衡？

答：负载均衡是把请求分发到多个服务实例。常见策略有轮询、随机、最少连接和一致性哈希。秒杀服务多实例部署时，入口请求会分散到多个 JVM。因为库存状态在 Redis 和 MySQL，不依赖单机内存，所以多实例能共享全局状态。这个也说明为什么 Java 单机锁不适合本项目。

### Q14. 网络抖动会影响什么？

答：网络抖动会造成延迟上升、超时和重试增加。对秒杀系统来说，重试会放大请求量，也可能导致重复下单风险。SETNX 幂等能挡住重复进入链路。MQ、Redis 和 MySQL 客户端也要设置合理超时，避免线程长时间挂住。高并发服务要假设网络不是稳定可靠的。

### Q15. 网络基础在项目里怎么体现？

答：它体现在连接复用、超时重试、幂等和限流上。Mini秒杀项目的每个外部依赖都是网络调用，Redis、MySQL、RabbitMQ 都可能超时。网络异常不能只靠 try catch，要从业务幂等和补偿上设计。面试时把 TCP 可靠传输和应用层幂等区分开，会显得理解更扎实。可靠传输不等于业务只执行一次。

## 25. 数据结构与算法 QA，至少 15 个

### Q1. 秒杀系统中可以用哪些数据结构？

答：秒杀系统里常见数据结构包括哈希表、队列、跳表、堆和布隆过滤器。Redis string 可以存库存，set 或 string key 可以做幂等，queue 对应 MQ 排队。限流可以用滑动窗口队列或计数器。TopK 热点统计可以用堆或近似算法。数据结构不是单独背，而是要服务具体业务问题。

### Q2. Redis zset 底层是什么？

答：Redis zset 在元素较少时会使用紧凑编码，元素较多时通常使用跳表和哈希表组合。哈希表用于按 member 快速查分数，跳表用于按 score 排序和范围查询。跳表实现比平衡树简单，范围查询性能也好。Mini秒杀项目当前没有用 zset，但排行榜、延迟队列和活动排序可能会用。回答时可以把底层和场景关联起来。

### Q3. 哈希表查询为什么快？

答：哈希表通过哈希函数把 key 映射到数组位置，理想情况下查询是 O(1)。冲突时会用链表、开放寻址或其他方式处理。Redis key 查找、Java HashMap 和很多缓存结构都依赖哈希思想。SETNX 能快速判断幂等 key 是否存在，也和 Redis 的字典结构有关。哈希表快，但要注意冲突和扩容成本。

### Q4. B+ 树查询复杂度？

答：B+ 树查询复杂度通常是 O(logN)。因为每个节点可以存很多 key，所以树高比二叉树低很多。数据库页大小固定，B+ 树能减少磁盘 IO 次数。MySQL 索引使用 B+ 树，非常适合等值和范围查询。项目里按 SKU 和用户 SKU 查询都依赖 B+ 树索引。

### Q5. 排序算法复杂度怎么回答？

答：常见排序里，快速排序平均 O(nlogn)，最坏 O(n^2)；归并排序稳定，时间 O(nlogn)，空间 O(n)；堆排序时间 O(nlogn)，空间 O(1) 但不稳定。插入排序适合小规模或近乎有序数据。面试时不用死背全部细节，要能说出适用场景。秒杀项目里排序不是主链路，但热点统计和榜单会用到。

### Q6. TopK 怎么做？

答：TopK 常见做法是维护一个大小为 K 的小根堆。遍历数据时，如果新元素比堆顶大，就替换堆顶并调整。复杂度是 O(nlogK)，适合海量数据里找前 K 个。秒杀里可以用 TopK 找热点 SKU 或高频用户。Redis 也可以用 zset 做实时排行。

### Q7. 限流算法有哪些？

答：常见限流算法有固定窗口、滑动窗口、漏桶和令牌桶。固定窗口简单但边界容易突刺。滑动窗口更平滑，但实现稍复杂。漏桶强调恒定流出，令牌桶允许一定突发。秒杀入口常用令牌桶或滑动窗口，配合业务维度限流。

### Q8. 令牌桶和漏桶区别？

答：令牌桶是按固定速率生成令牌，请求拿到令牌才能通过，可以允许短时间突发。漏桶是请求先进桶，再按固定速率流出，更强调平滑输出。令牌桶适合允许一定突发流量的接口，漏桶适合保护下游稳定处理。秒杀场景通常希望入口可控，也要允许短峰，所以令牌桶很常见。具体选择要看业务承受能力。

### Q9. LRU 怎么实现？

答：LRU 可以用哈希表加双向链表实现。哈希表负责 O(1) 定位节点，双向链表维护访问顺序。访问或更新时把节点移动到头部，淘汰时删除尾部。Java 可以用 `LinkedHashMap` 简化实现。缓存系统里 LRU 用来淘汰最近最少使用的数据。

### Q10. 布隆过滤器是什么？

答：布隆过滤器是一种空间效率很高的概率数据结构。它可以判断一个元素一定不存在，或者可能存在。它会有误判，但不会漏判不存在。缓存穿透场景可以用布隆过滤器挡住大量不存在 key 的请求。秒杀活动可以用它判断 SKU 是否属于活动集合，但不能用它判断库存。

### Q11. 队列在项目里怎么体现？

答：RabbitMQ 本质上就是队列思想。请求进入队列后，消费者按自己的能力处理，实现削峰。队列能把瞬时流量变成有序等待，但也会带来延迟和积压问题。Mini秒杀项目返回排队中，就是承认队列里的中间状态。面试时可以把 MQ 和基础队列数据结构联系起来。

### Q12. 跳表为什么适合范围查询？

答：跳表通过多层索引加速链表查找。底层链表保持有序，上层索引可以快速跳过大量节点。查到范围起点后，可以沿底层链表顺序遍历。Redis zset 使用跳表就是因为它适合有序集合的范围查询。它实现比红黑树简单，性能也稳定。

### Q13. 一致性哈希是什么？

答：一致性哈希把节点和 key 映射到一个环上，key 顺时针找到负责节点。节点增减时，只影响环上一小段 key，减少迁移量。它常用于缓存分片和负载均衡。Redis Cluster 使用槽位机制，不完全等同一致性哈希，但目标也是分片。秒杀库存分片时可以借鉴这种思想。

### Q14. 如何找重复订单？

答：在线系统里靠唯一索引防止重复订单生成。离线排查可以用 SQL 按 `user_id, sku_id` 分组，找 `COUNT(*) > 1` 的记录。算法上这相当于用哈希分组统计。项目压测验收就可以用这个 SQL。正确系统应该让这个查询没有结果。

### Q15. 算法基础在项目里怎么体现？

答：它体现在限流、排队、索引、缓存和热点统计里。哈希表对应 Redis key 查找和幂等判断，队列对应 MQ 削峰，B+ 树对应 MySQL 索引，堆可以做 TopK 热点统计，布隆过滤器可以防穿透。面试时不用强行把复杂算法塞进项目，而是讲清楚常用数据结构如何支撑服务端性能。这样更自然，也更符合后端岗位。

## 25.1 新补 8 个优化点口播版

### Q1. 你后面又补了哪些能力？

答：我后面主要补了 8 块，都是围绕秒杀主链路的工程补强，不是去做完整电商。第一是 MySQL 分段库存，把数据库扣减热点从一行拆成多个 segment 行。第二是售罄本地标记，库存扣空后短时间在应用本机挡掉无效请求。第三是本地消息表状态机，从 PENDING、SENDING、SENT 到 CONSUMED，失败后能进入 DEAD。第四是消息回放和补偿记录，失败消息可以按 requestId 重投。第五是动态限流规则，可以按活动和 SKU 临时调阈值。第六是 Redis Cluster 故障脚本，第七是 Actuator 和 Micrometer 指标，第八是分页对账和补偿表。

### Q2. 为什么要做 MySQL 分段库存？

答：原来消费者落库时是扣一行 SKU 汇总库存，高并发下所有订单都会竞争同一行，这个行锁会非常热。现在我新增了 `sku_stock_segment`，初始化库存时把库存拆成多个库存段。消费者事务里先插订单，再按 User ID hash 到某个 segment 扣减，失败时再兜底找其他有库存的 segment。这样数据库层面的写热点从一行拆成多行，锁竞争会下降。`sku_stock` 还保留，但更多是汇总视图，对账时会同步。这个版本仍然是个人项目简化版，生产级还要结合压测决定 segment 数和订单分库分表。

### Q3. 分段库存会不会影响防超卖？

答：不会，因为每个 segment 的扣减 SQL 仍然带“可用库存大于 0”这个条件。也就是说，不管请求并发多高，MySQL 单个 segment 行也不会被扣成负数。Redis 前面已经先用 Lua 扣了入口库存，MySQL segment 是最终兜底。订单插入和 segment 扣库存还是在同一个事务里，如果扣库存失败，订单插入会回滚。唯一索引继续防重复订单。这个设计的核心不是改变正确性，而是把数据库热点拆散。

### Q4. 售罄本地标记解决什么问题？

答：它解决的是库存卖完之后的无效请求空打问题。秒杀后半段经常是库存已经没了，但用户还在疯狂刷新，如果每个请求都打 Redis Lua，Redis 还是会有压力。现在 Redis Lua 返回库存不足时，本机用 Caffeine 做一个短 TTL 的 sold-out 标记。后续同一个活动 SKU 的请求会先在应用内快速失败，不再打到 Redis。这个标记不是最终事实，所以 TTL 很短，而且初始化、预热、Redis 恢复和对账修复库存时都会清掉。面试时可以说这是入口优化，不是库存事实。

### Q5. 动态限流是怎么做的？

答：原来限流阈值主要写在配置文件里，调整不够灵活。现在我新增了 `seckill_rate_limit_rule`，按活动 ID 和 SKU ID 存一组限流规则，比如 SKU 维度、用户维度、IP 维度的窗口阈值。入口限流时先查短 TTL 本地缓存，缓存没有再查数据库，避免每个请求都打 MySQL。查不到规则就回退到 `application.yml` 的默认值。这个设计适合面试讲“活动期间临时调参”，但生产级还要做配置中心、灰度发布和权限审计。当前 admin 接口没有鉴权，只是个人项目演示入口。

### Q6. MQ 状态机比之前强在哪里？

答：之前只说本地消息表加 confirm，状态比较粗。现在状态机更清楚：请求先是 PENDING，发送前标 SENDING，Broker confirm 成功后是 SENT，消费者落库成功后是 CONSUMED。如果发送失败、confirm 失败或路由失败，会进入可重试状态，并写 next retry at 做退避重试。超过最大重试次数后标 DEAD，不再无限重试。后面可以通过回放接口按 requestId 重投，重复消费仍然靠联合唯一索引兜底。这个口径比简单说“用了 MQ”更像真实服务端链路。

### Q7. 死信和回放怎么讲？

答：消费者遇到不可预期异常时，会把本地消息标成 DEAD，并 nack 到 RabbitMQ 的死信队列。这个个人项目没有直接读取 RabbitMQ 死信队列里的原始消息，而是用本地消息表作为回放依据。回放接口会根据 requestId 重建消息，再投递回 RabbitMQ。这样即使消息被重复回放，消费者插订单时也会被 User ID 和 SKU ID 的联合唯一索引挡住。生产级会做得更完整，比如死信告警、后台审核、操作审计、批量回放和人工补偿工单。面试里要坦诚说这是可靠消息的骨架，不是完整生产后台。

### Q8. 对账和补偿现在怎么做？

答：现在对账不是只扫最近更新的库存，而是按 `sku_stock.id` 分页扫描。开启 MySQL 分段库存时，对账会先汇总 segment 的可用库存和已售数量。Redis 期望库存按“MySQL 可用库存减未完成消息数”计算，避免把已经排队但还没落库的请求重复释放。发现 Redis 库存不一致时，会修复总库存和 bucket 库存，并写入 `seckill_compensation`。如果 MySQL 订单成功数和库存 soldCount 不一致，也会写补偿记录等待人工检查。生产级还要做恢复进度表、告警、人工审批和幂等补偿任务。

### Q9. Actuator 和指标有什么用？

答：指标主要是为了让系统不是黑盒。现在项目接入了 Spring Boot Actuator、Micrometer 和 Prometheus registry，可以看健康检查、基础 metrics 和 Prometheus 格式指标。自定义指标包括入口结果、Redis 扣库存结果、MQ 消费结果、订单结果和回放结果。比如压测时可以看 rate limited、queued、deduct success、dead lettered 这些结果的计数变化。生产级还要接 Grafana、告警规则和链路追踪。个人项目里做到这个程度，面试时已经能说明我知道高并发系统必须可观测。

### Q10. Redis Cluster 故障脚本怎么讲？

答：我现在不只提供 Redis Cluster compose，还补了停止和恢复节点的 PowerShell 脚本。脚本可以停掉一个 Redis Cluster 节点，然后查看 cluster info 和 cluster nodes，观察集群是否还能保持可用。这个主要是故障演练入口，不是完整混沌工程。面试时要说清楚，Redis Cluster 解决容量和节点故障切换，但不能自动解决单个超级热 key。真正的热点库存还要靠 bucket 分片、token 资格池、限流和本地售罄标记一起处理。这样回答会比“我用了 Redis Cluster 所以能抗 10 万”更严谨。

## 26. 最后 30 分钟背诵版

### 1. 30 秒项目介绍

Mini秒杀项目是一个个人实现的高并发秒杀下单样板项目，重点不是完整电商，而是服务端下单链路。它先用活动状态机控制入口，再用短 TTL token 和动态限流挡掉异常流量。真正下单时，用 Redis Lua 做限流，用 Redis Set-N-X 防重复请求，用 Redis Lua 扣分片库存，再用本地消息表加 RabbitMQ 做异步削峰。消费者异步创建订单，MySQL 事务、分段库存和联合唯一索引保证最终正确。Redis 负责抗高并发，MQ 负责削峰，MySQL 负责最终事实，本地消息状态机、confirm、退避重试、DEAD 回放、排队超时、分页对账和 Redis 恢复态负责异常恢复。

### 2. Redis Lua 防超卖

我防超卖用了两层。第一层是 Redis Lua，脚本在 Redis 内部原子执行，先判断库存是否存在和是否大于 0，再执行 DECR。现在 Redis 库存还做了 bucket 分片，按用户 hash 选择分片，降低单热点 key 压力。第二层是 MySQL 条件更新，扣库存 SQL 里有“可用库存大于 0”。新版还把 MySQL 库存拆成多个 segment，降低单行锁竞争，但每个 segment 仍然有条件扣减兜底。Redis 负责入口抗并发，MySQL 负责最终事实。

### 3. Set-N-X + 唯一索引防重复

我防重复下单有三层。第一层是短 TTL token，用户必须先拿 token，提交后 token 会被删除，降低重放风险。第二层是 Redis Set-N-X 写活动、用户、SKU 维度的幂等 key，同一用户同一活动 SKU 只有第一次能设置成功。第三层是数据库联合唯一索引兜底。即使 HTTP 重试、重复点击或 MQ 重复消费，也不会创建重复订单。

### 4. MQ 异步削峰

秒杀请求如果同步写 MySQL，数据库连接池和库存行锁会承受瞬时高峰。项目里 Redis 扣库存成功后先写本地消息表，再发送 RabbitMQ，接口先返回排队中。生产者发送前标 SENDING，confirm 成功后标 SENT，消费成功后标 CONSUMED，失败会按 next retry at 做退避重试。超过重试上限会进入 DEAD，可以通过 requestId 回放。消费者按可控并发慢慢写 MySQL，让数据库压力变平滑。这个项目用本地消息表、confirm、手动 ACK、唯一索引、死信结构和回放接口来说明可靠消费思路。

### 5. Redis/MySQL 最终一致性

Redis 是入口库存，MySQL 是最终事实。下单时 Redis 先扣分片库存，MQ 消费后 MySQL 再扣 MySQL 分段库存，所以中间会有短暂不一致。正常情况下，消息消费完成后两边会收敛。异常时，MQ 发送失败会记录本地消息表并退避重投，消费失败会进入 DEAD 和补偿记录，排队太久会被定时任务标记为超时。Redis 宕机后入口会进入恢复态，恢复时按 MySQL 可用库存减未完成消息数重建 Redis，避免重复释放已经排队的入口资格。对账任务会分页扫描库存并写补偿记录，方便后续人工检查。

### 6. 项目不足与生产级改进

这个项目是个人简化版，没有登录、支付、优惠券和完整风控。当前已经有活动状态、token、防刷限流、动态限流、Redis 库存分片、Redis Cluster 演示、MySQL 分段库存、本地消息状态机、confirm/return、退避重试、DEAD 回放、排队超时、分页对账、补偿记录和 Redis 宕机恢复入口。生产级我会加真实网关限流、验证码或风控，Redis 做云上高可用、恢复编排和热点监控，MQ 加告警、审核和人工重放后台。MySQL 侧会做分库分表、慢 SQL 和锁等待监控，指标侧会接 Prometheus、Grafana 和链路追踪。我的表达重点是：个人项目不夸大，但设计方向参考真实高并发业务。

### 7. 一句话收尾

这个项目我最想展示的是后端链路设计能力：入口用 Redis 抗并发，中间用 MQ 削峰，落库用 MySQL 事务和索引兜底，异常用本地消息表、死信和对账补偿保证可恢复。
