# 和开源项目对比

## 总体定位

很多开源秒杀项目偏“完整 demo”：有登录页、商品页、页面静态化、验证码、隐藏地址、Redis 预扣和 MQ 异步。MiniSeckill 的定位不同，它更偏“服务端面试证据链”：把秒杀下单主链路、可靠消息、恢复、对账和真实压测材料做清楚。

面试时不要说“比所有开源项目都强”。更稳妥的说法是：

> 我参考了常见秒杀项目的分流、限流、缓存和异步思路，但这个项目重点补了本地消息表、MQ confirm/return、重试回放、Redis 恢复、对账补偿和真实压测报告。它不是生产级完整电商，用户态、验证码和监控也只是 demo/骨架级，不是完整商城页面系统。

## 常见开源项目具备什么

从 `springboot-seckill`、`hfbin/Seckill`、`spring-boot-seckill`、`dis-seckill` 这类项目看，常见能力包括：

- 登录和用户模拟。
- 商品列表、商品详情、订单详情页面。
- 页面缓存、对象缓存、页面静态化。
- 验证码或数学题防刷。
- 隐藏秒杀接口地址。
- Redis 预扣库存。
- 本地标记减少 Redis 空打。
- RabbitMQ 或 Kafka 异步下单。
- 数据库唯一约束和条件扣库存防超卖。
- Nginx、网关、微服务拆分等架构方向。

这些能力有些偏前端演示，有些偏入口防刷，有些偏生产架构说明。

## MiniSeckill 已经做了什么

本项目已经落地的部分：

- 活动状态校验和活动时间窗口。
- 可选 JWT demo 用户态。
- 可选数学验证码。
- 短 TTL 秒杀 token。
- 短 TTL 隐藏下单 path。
- token 资格池，限制进入下单链路的 token 总量。
- Redis ZSET 滑动窗口限流，并保留固定窗口回退。
- Redis 用户 SKU 幂等。
- Redis 分片库存单 Lua 扣减，Cluster 配置回退兼容路径。
- 雪花订单 ID、动态规则负缓存、Redis-first 查重和高频日志异步化。
- 本地消息表。
- RabbitMQ confirm ack、nack 和 return。
- MQ 重试、重试耗尽 DEAD、管理接口回放。
- 消费者手动 ack、`CONSUMING` CAS、stale `CONSUMING` 租约恢复和重复消费幂等。
- MySQL 事务内插订单和扣库存。
- MySQL 分段库存。
- 本地售罄标记。
- Redis 健康检查、恢复态和库存重建。
- 定时库存对账、补偿记录和排队超时。
- Actuator/Micrometer 指标。
- Swagger/OpenAPI 接口文档。
- 多阶段 Dockerfile、Nginx compose、Prometheus/Grafana provisioning。
- k6 压测脚本、reset/verify 脚本和原始结果文件。

## MiniSeckill 更强的地方

### 1. 有真实压测证据

很多 demo 只有设计说明或 README 截图。这个项目有 `REPORT.md` 和 `benchmark/evidence/mac-arm64/`，能给出同机同参三轮对比：

- 不同用户成功入队 p95：8.17 ms → 5.49 ms，下降 32.8%。
- 重复请求成功入队 p95：7.92 ms → 4.76 ms，下降 39.9%。
- 售罄尾部整体 HTTP p99：98.27 ms → 12.04 ms，下降 87.7%。
- 全开对照中动态规则查询 1999 → 7，用户订单事实查询 4501 → 1000。
- 数据库成功订单未超过库存，重复订单组为 0。

这让面试回答更可信。

### 2. 可靠消息链路更完整

普通 demo 常见做法是“Redis 预扣成功后直接发 MQ”。MiniSeckill 多了本地消息表和状态机：

```text
PENDING -> SENDING -> SENT -> CONSUMING -> CONSUMED
失败状态 -> 重试 -> DEAD -> 回放
```

这样能回答“MQ 发送失败怎么办”“confirm nack 怎么办”“消息一直排队怎么办”“超时和消费竞争怎么办”“怎么回放”。

最新版还补了 `CONSUMING` 处理租约：如果消费者在处理中崩溃，恢复任务会按 MySQL 订单事实把消息补成 `CONSUMED`，或者回退为 `FAILED` 交给 retry job 重投。这比只加一个中间态更严谨。

### 3. Redis 故障恢复有闭环

项目不是只说 Redis 高可用，而是写了恢复态和恢复公式：

```text
expectedRedisStock = max(0, mysqlAvailableStock - unfinishedMessages)
```

旧 Windows 历史故障注入记录过 Redis 宕机场景：不是无感恢复，而是 fail-closed，恢复后对账一致。当前 Mac 报告只做优化前后性能对比，不把这组跨机历史数据混入百分比。这种边界比空泛说“高可用”更可信。

### 4. 热点拆分能落到代码

Redis 侧有 bucket 库存，MySQL 侧有 segment 库存。面试时可以解释两层热点：

- Redis 单 key 热点用 bucket 拆。
- MySQL 单行库存热点用 segment 拆。

同时也能承认边界：单 Lua 只适用于同一 Redis 节点，Cluster 需要回退或重新设计 hash tag；segment 不是分库分表，最终还需要对账和真实多机压测。

## MiniSeckill 弱于完整开源项目的地方

### 1. 用户和权限体系只是 demo 级

当前补了可选 JWT demo 用户态，开启后会校验请求 `userId` 和登录用户一致。但它没有用户表、注册流程、密码加密、刷新 token、RBAC 和 token 黑名单。`/api/admin/**` 已经补了可选共享 token 保护和日志型审计，但还不是完整登录态、角色权限、审计表和操作后台。

### 2. 防刷还是演示级

项目已经补了短 TTL `orderPath`、`/api/seckill/order/{orderPath}` 和可选数学验证码，但旧 `/order` 为了压测脚本仍然保留，验证码也不是图片/滑块/风控平台。设备指纹、黑名单和网关层校验仍是后续生产化方向。

### 3. 没有页面层

项目没有商品页、订单详情页、页面缓存和页面静态化。它更适合后端面试，不适合展示完整商城体验。

### 4. 没有生产级集群验证

仓库有 Redis Cluster、多实例和 Nginx 示例，但没有云上多机压测、MQ 集群、MySQL 分库分表、监控告警和灰度发布。

### 5. 测试体系还不够

当前已有单元测试、MockMvc、Luaj、JaCoCo 和 CI，覆盖滑动窗口、分片单 Lua、动态限流负缓存、雪花 ID、HTTP 双层语义、消费者状态机、`CONSUMING` 租约恢复和排队超时；Testcontainers 覆盖真实 Redis 并发扣减与 MySQL Mapper。仍缺少 RabbitMQ 和完整下单链路的容器组合测试。

## 面试对比话术

可以这样说：

> 常见开源秒杀 demo 会重点做页面静态化、隐藏地址、验证码、Redis 预扣和 MQ 异步。我这个项目没有做完整商城页面，而是把后端主链路往工程闭环补：默认滑动窗口、Redis 分片库存单 Lua、雪花订单 ID、本地消息表、RabbitMQ confirm/return、`CONSUMING` 租约恢复、MySQL 条件库存、失败订单留痕、重试回放、Redis 恢复和库存对账。压测不是写概念，而是保留同机同参三轮对比和数据库/MQ 对账证据。

如果面试官问“为什么不做完整用户中心和页面”，可以回答：

> 这是我有意收敛的范围。完整用户中心、RBAC、页面静态化和商品详情页是电商系统能力，但这个项目主要想展示服务端下单链路和一致性。当前已经补了 demo JWT、数学验证码、隐藏 path 和 admin 共享 token。如果继续做，我会把用户侧升级成真实用户表和刷新 token，把 admin 升级成 RBAC/审计表，再把验证码和网关层校验接到风控策略，而不是直接堆页面。
